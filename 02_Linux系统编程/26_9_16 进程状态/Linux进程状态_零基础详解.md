## 1.1 先理解：程序、进程、CPU 与“等待”

### 1.1.1 程序启动后，系统到底在管理什么

**程序是“写好的步骤”，进程是“正在进行的一次执行”。**例如，`sleep_demo.c` 是 C 源代码；编译生成的 `sleep_demo` 是可执行文件。可执行文件放在硬盘上时不会自己运行；输入 `./sleep_demo` 后，系统建立一次执行所需的资源与管理信息，程序才开始执行。同一个可执行文件启动两次，通常就会产生两个不同的进程，各自有自己的运行位置和进程编号。

这里的“正在进行”不等于“每一瞬间都在 CPU 上计算”。就像一项任务尚未结束，执行者可能正在处理，也可能在等待材料：任务仍然存在，但当前并不一定在做计算。进程状态就是操作系统用来区分这些情况的信息。

| 名词 | 从零理解 | 在本章中的作用 |
|---|---|---|
| CPU | 执行机器指令的处理器 | 进程只有获得执行机会，代码才能向前推进 |
| 内存 | 保存正在使用的代码、数据及管理信息的存储空间 | 等待中的进程也可能保有内存，不是只有正在执行的进程才占内存 |
| 操作系统内核 | 管理 CPU、内存、设备和进程等资源的核心程序 | 决定调度谁、记录谁在等待、处理退出与回收 |
| 进程控制块（PCB） | 教材对“一份进程管理记录”的抽象称呼 | 可以理解为系统保存的进程档案，而不是程序源代码 |
| `task_struct` | Linux 内核中的任务描述结构体 | 包含或关联状态、标识、调度、内存等管理信息 |
| PID | Process ID，进程编号 | 用来指定“我在观察、管理哪一个进程” |
| PPID | Parent Process ID，父进程编号 | 用来追踪“谁创建或当前收养了这个进程” |
| Shell | 解释并执行用户命令的程序，例如 Bash | 你输入命令后，通常由 Shell 启动外部程序、管理前后台作业 |

PCB 是抽象概念，`task_struct` 是 Linux 的具体实现组成部分，不能理解为“把程序所有内存内容塞进一个结构体”。很多资源通过其他结构体和指针关联。严格地说，Linux 调度的是任务/线程；一个多线程进程中的不同线程可以处于不同状态。本章先用单线程进程讲解，这样一个示例进程对应一条主要执行流，不会混入多线程细节。[依据：内核任务结构与调度接口][kernel-sched]、[Linux 调度手册][sched]

**一个父子关系例子：**

```text
Bash（PID=2000）
└─ 你启动的程序（PID=3000，PPID=2000）
   └─ 它通过 fork 创建的子进程（PID=3001，PPID=3000）
```

这里的数字只是示意。PID 不一定连续，每次运行也可能不同。`getpid()` 读取当前进程自己的 PID，`getppid()` 读取它当前的 PPID；“当前”很重要，因为原父进程退出后，PPID 可能改变，而这个子进程自己的 PID 不因此改变。[依据：getpid(2)][getpid]

**系统调用是什么？**普通程序不能随意改内核的管理记录，也不能自行决定占用哪个 CPU。程序需要请求内核提供服务，例如创建进程、读取数据、等待子进程，这类受控入口称为系统调用。我们在 C 里调用的 `fork()`、`waitpid()` 等接口通常还经过 C 库封装；不必把“C 函数名”与“每种机器架构上同名的底层系统调用”强行一一对应。[依据：fork(2)][fork]、[wait(2) 的库与内核差异说明][wait]

### 1.1.2 为什么不能让每个进程一直占着 CPU

假设暂时只考虑一个逻辑 CPU，有三个进程：A 需要计算，B 等待键盘输入，C 等待网络数据。如果让 B 在没有输入时一直占用 CPU，CPU 只能反复检查“输入来了吗”，而真正有工作可做的 A 却得不到机会。这就是为什么系统需要区分“可以继续执行”和“暂时不能继续执行”。

操作系统通过**调度器**选择接下来执行的任务。某个任务暂时让出 CPU 时，系统保存足够的执行现场，例如指令运行到哪里、寄存器中的值；以后再获得 CPU，就从相应位置继续，而不是从 `main()` 重新开始。这个切换过程称为**上下文切换**。在多核机器上，不同逻辑 CPU 可以同时执行不同任务；但“能执行的任务多于当前执行位置”时，仍然需要调度。[依据：sched(7)][sched]

先把教材中最核心的三种状态区分清楚：

| 状态 | 缺少的是什么 | CPU 现在给它，能否继续做后续工作 | 例子 |
|---|---|---|---|
| 就绪 | 只缺 CPU 执行机会 | 可以 | 计算所需数据已经齐全，正在排队 |
| 运行 | 已经获得 CPU | 正在执行 | 执行加法、判断、函数中的指令 |
| 阻塞/等待 | 缺某个事件或条件 | 单靠给 CPU 也无法完成等待的操作 | 没有键盘输入、没有网络数据、等待子进程退出 |

**就绪和阻塞都可能没在 CPU 上运行，但原因不同。**就绪是“条件齐了，轮到我就能做”；阻塞是“条件没齐，轮到我也做不了”。因此，等待事件完成后，一般先变为就绪，再由调度器决定什么时候真正执行。

```text
等待 CPU：事情能做 → 排队 → 获得 CPU → 开始做
等待事件：事情暂时做不了 → 条件满足 → 进入可运行状态 → 再等 CPU
```

**阻塞不是电脑卡死，也不一定是程序错误。**一个服务器大部分时间在等请求，终端中的 Shell 在等用户输入，这些都可能是正常工作。要判断异常，需要结合“在等什么、等多久、业务本来应当做什么”，不能看到睡眠状态就说程序坏了。

**唤醒也不等于立即执行。**唤醒的核心含义是让符合条件的任务重新具备运行资格。任务被唤醒时，CPU 可能正忙于其他任务；重新获得 CPU 后，才继续检查条件、执行代码。即使被唤醒，也可能发现条件已被其他任务消耗而再次等待，所以“唤醒”不是“业务必然成功”的同义词。[依据：内核等待条件与唤醒说明][kernel-wait]

**进程状态与用户态/内核态是两种分类。**`R/S/D/T/Z` 关注任务当前处于怎样的生命周期或调度状态；用户态、内核态关注正在以什么权限执行哪一类代码。例如，一个 `R` 状态任务可以在执行用户程序，也可以在内核中处理系统调用。不能把“用户态”直接当作 `R`，把“内核态”直接当作 `D`。[依据：Linux 调度与进程信息接口][sched]、[内核任务结构][kernel-sched]

## 1.2 看懂原图：七状态模型、Linux 字母状态及其转换

### 1.2.1 第一张图为什么有七种状态，而 Linux 不这样逐项显示

你上传的第一张图包含：创建、就绪、运行、阻塞、结束、就绪挂起、阻塞挂起。它是**教材层面的通用七状态模型**，目的是解释调度与挂起，不是说运行 `ps` 必定能看到七个一一对应的字母。

先沿“创建 → 就绪 → 运行”看主线，再看运行后分出的三个方向：暂时让出 CPU、等待事件、结束。最后再看图下方的挂起部分，不要一开始就在所有箭头之间来回跳。

| 图中节点 | 实际表达的意思 |
|---|---|
| 创建状态 | 正在建立管理记录和所需资源，尚未按图中的流程进入正常执行 |
| 就绪状态 | 已具备执行条件，只差 CPU |
| 运行状态 | 正在获得 CPU 执行 |
| 阻塞状态 | 因等待事件，暂时不具备继续完成该操作的条件 |
| 结束状态 | 执行已经结束，进入清理流程；教材的“结束”不细分 Linux 的所有退出阶段 |
| 就绪挂起状态 | 除挂起限制外，执行条件已满足；解除挂起后可以回到就绪 |
| 阻塞挂起状态 | 同时有两个障碍：还在等待事件，而且处于挂起状态 |

这里的“挂起”常用于教材的中级调度、进程换出等讨论，可以先理解为**系统额外施加的暂不参与正常调度的限制**。传统模型常把它和把进程的部分执行映像换出到外存联系起来。外存主要指硬盘等持久存储；换出不等于删除进程，也不是把所有管理信息一并丢掉，否则系统就无法再找到并恢复它。

**逐条解释原图的箭头：**

| 原图箭头 | 发生了什么 | 不要误解成什么 |
|---|---|---|
| 创建 → 就绪 | 创建完成，允许参加调度 | 创建完成就必定已经在 CPU 上执行 |
| 创建 → 就绪挂起 | 创建后暂时不让它进入正常调度 | 创建失败或者进程已经死亡 |
| 就绪 → 运行，标注“被调度” | 调度器选中了它，并分配执行机会 | 进程自己随意抢占 CPU |
| 运行 → 就绪，标注“时间片用完” | 暂时换其他任务执行，自己仍具备运行条件 | 没有 CPU 就等于阻塞 |
| 运行 → 阻塞，标注“等待事件” | 当前操作需要的条件还没满足 | 程序结束 |
| 阻塞 → 就绪，标注“事件完成” | 等待的条件满足，可以重新参加调度 | 事件一完成就立刻独占 CPU |
| 运行 → 结束 | 执行结束，进入清理 | `ps` 在同一瞬间必定已经查不到 |
| 就绪 → 就绪挂起 | 对本来可运行的进程施加挂起限制 | 产生了一个新的等待 I/O 的条件 |
| 就绪挂起 → 就绪，标注“激活” | 解除挂起限制，重新具备被调度资格 | 直接跳到正在执行 |
| 阻塞 → 阻塞挂起 | 原有等待尚未结束，又被挂起 | 原来的等待事件已经完成 |
| 阻塞挂起 → 阻塞，标注“激活” | 只解除挂起，但所等事件仍未完成 | 激活能自动解决原来的资源等待 |
| 阻塞挂起 → 就绪挂起，标注“事件出现” | 所等待的事件满足了，但挂起限制还在 | 事件完成就自动解除挂起 |
| 运行 → 就绪挂起，图外侧长箭头“挂起” | 停下当前执行并进入挂起；本来并没有欠缺等待条件 | 必须先发生 I/O 等待才能挂起 |

图中的“事件出现”，在这条箭头上应理解成“**原先所等待的事件发生，等待条件被满足**”，不是“又出现了一个新的问题”。

可以用一个两条件表理解图下半部分：

```text
                    所等事件未完成       所等事件已完成/本来无需等待
没有挂起限制            阻塞                       就绪
仍有挂起限制          阻塞挂起                   就绪挂起
```

**为什么不直接把“挂起”对应成 Linux 的 `T`？**因为教材换出、Linux 内存分页、Shell 的作业暂停和调试器暂停不是完全相同的概念。Linux 的 `T` 主要表示由作业控制信号造成的停止，不是在说“整个进程已经被搬到硬盘”。一个 Linux 进程的部分内存页被换出，也不意味着 `ps` 必须显示某个“就绪挂起”字母。[对照：ps(1) 的状态定义][ps]

### 1.2.2 Linux 的 R、S、D、T、t、Z、X、I 到底是什么意思

先记住总表，随后逐个理解，尤其注意“中文简称”不能替代完整含义。

| 字母 | 常见英文 | 正确理解 | 是否已经结束执行 |
|---|---|---|---|
| `R` | running / runnable | 正在运行，或处于可运行状态等待 CPU | 否 |
| `S` | interruptible sleep | 可中断睡眠，正在等事件，允许适当的信号打断等待 | 否 |
| `D` | uninterruptible sleep | 不可中断睡眠，常见于某些内核等待路径 | 否 |
| `T` | stopped | 被作业控制信号停止，等待继续等处理 | 否 |
| `t` | tracing stop | 在跟踪、调试过程中被暂停 | 否 |
| `Z` | zombie | 已经终止执行，但退出信息还没有被回收 | 是 |
| `X` | dead | 内部退出清理中的死亡标记，正常使用 `ps` 不应看到 | 是 |
| `I` | idle | 空闲的内核线程，普通应用实验通常不需要重点研究 | 不是“应用进程退出” |

这张表是用户可见状态的入门归纳，不表示 Linux 内部只存在这些标志。状态定义以及大小写区别见 [ps(1)][ps]；`/proc/PID/status` 也会提供可读的状态名称。[proc_pid_status(5)][proc-status]

**① `R`：可以运行，不保证采样时正在占用 CPU。**

假设单个逻辑 CPU 上有 A、B 两个计算任务，当前 A 在执行，B 等着轮到自己。这两个任务都可能是 `R`。A 的 `R` 对应“正在运行”，B 的 `R` 对应“就绪”。因此 Linux 把教材中这两种情况归入同一个可运行状态，不能看见 `R` 就断言“它这一刻一定在某个 CPU 上执行”。

时间片结束、被抢占之后，如果没有新的等待条件，任务仍然是 `R`。变化的是“谁现在真正执行”，而不是一定从 `R` 变成 `S`。教材用“时间片耗尽”帮助理解轮流执行，但不要继续推导成“Linux 所有调度策略都使用完全相同的固定时间片”。[依据：ps(1)][ps]、[sched(7)][sched]

**② `S`：进程活着，只是现在在等。**

常见例子是 `sleep(1)` 等待一秒钟过去，`read()` 等待终端输入，或父进程通过 `waitpid()` 等待子进程结束。等待期间，它不需要持续执行自己的业务指令。条件满足后，它重新进入可运行状态，获得 CPU 后才执行后续语句。[依据：sleep(3)][sleep]、[wait(2)][wait]

“可中断”里的“中断”在这里主要指**允许某些信号使等待提前结束或改变控制流程**，不是“CPU 的任何硬件中断都会把这个进程叫醒”。信号可以先理解为内核向进程传递的事件通知，例如“请求结束”“请求暂停”“子进程状态改变”。有些信号被忽略，有些被暂时阻塞，有些使进程终止，有些交给程序处理；不能说任何信号到来后，等待操作都会成功完成。[依据：signal(7)][signal]

例如，一个等待输入的进程因信号而返回，并不意味着用户刚刚输入了数据。某些接口可能报告 `EINTR`，意思是“这次等待被信号中断”，程序需要决定重试还是退出。后面的 `waitpid()` 实验会把重试逻辑写出来。

**为什么程序每秒都打印一句话，反复执行 `ps` 却几乎一直是 `S`？**因为打印和少量判断可能只占很短时间，绝大部分时间都在 `sleep(1)`。你每次运行 `ps` 都只是重新取一个快照，快照多半还是落在那段更长的睡眠区间里。

```text
实际过程：短暂执行 → 睡约 1 秒 → 短暂执行 → 睡约 1 秒 → ……
采样结果：              S                      S
```

这不是“第一次观察碰巧睡着，第二次就一定会看到运行”。即便连续观察很多次，也可能一直错过极短的 `R` 区间；人为用固定节奏采样还可能反复落在相近阶段。**能持续看到新的输出，说明进程中间确实获得过执行机会；多次 `S` 快照不能推翻这一点。**这是由程序执行时间分布推导出的观察结果，不是 `ps` 被缓存住了。

**③ `D`：不是“在睡得更沉”，而是等待路径不按普通信号方式被打断。**

`D` 常被显示成 `disk sleep`，但不能只按字面理解成“只有读硬盘才会出现”。它可能涉及存储、文件系统、驱动等内核等待。反过来，**并非所有 I/O 等待都是 `D`**：等终端输入、网络事件等常见等待也可能是 `S`。具体取决于相应内核路径怎样实现等待。[依据：ps(1)][ps]、[内核状态标志][kernel-sched]

为什么需要这种等待方式？某些内核操作不能任意在中间跳走，否则会给资源一致性、操作收尾或调用约定带来问题。此时任务等待条件满足，再继续走后面的内核流程。对入门学习而言，应理解成“这段等待不能简单用普通信号立刻打断”，不要想象成“内核禁止任何中断发生”。

**为什么 `kill -9` 后可能仍然是 `D`？**`SIGKILL` 不能被程序捕获、忽略或阻塞，但这不等于任何内核等待都能在发送信号的瞬间安全结束。对于真正不可中断的等待，终止请求可能要等到任务离开该等待路径后才能完成。`kill` 成功返回，也只说明发送请求成功，不等于目标进程已经完全消失。[依据：signal(7)][signal]、[kill(2)][kill2]、[内核状态定义][kernel-sched]

进一步说，Linux 还有 `TASK_KILLABLE` 等组合状态，在相关等待中可以响应致命信号。因此也不要背成“凡是 `ps` 显示 `D`，任何信号永远没用”。排查长期 `D` 的重点是它卡在哪个等待条件、底层资源是否故障，而不是不断重复 `kill -9`。本笔记不通过破坏设备、挂死磁盘等方法强行制造 `D`。

**④ `T`：被暂停，程序还没有结束。**

对一个普通实验进程发送 `SIGSTOP`，它会停止执行；之后发送 `SIGCONT` 可以解除这种停止，让它恢复到适当的执行或等待流程。`SIGSTOP` 不是“让它休息一秒”，没有一个固定倒计时自动恢复；它与 `sleep(1)` 不是同一回事。[依据：signal(7)][signal]

在交互式终端中按 `Ctrl+Z`，通常由终端向前台进程组发送 `SIGTSTP`。它的默认动作也是停止，但与不可捕获的 `SIGSTOP` 不同，`SIGTSTP` 可以被程序捕获或忽略。之后使用 `fg` 或 `bg` 可以继续该 Shell 管理的作业。`Ctrl+C` 通常发送的是 `SIGINT`，默认动作是终止，不是暂停。[依据：Bash 作业控制][bash]、[signal(7)][signal]

**⑤ `t`：小写，通常与调试器有关。**

`T` 和 `t` 不是排版差异。小写 `t` 表示跟踪暂停，例如调试器控制目标进程时的停点。`ptrace()` 是 Linux 提供给跟踪、调试程序的一组接口，不是一个用来解决僵尸进程的函数。对调试暂停，应按调试器的恢复机制处理，不能把所有情况都简化成“发一个 `SIGCONT` 就够了”。[依据：ps(1)][ps]、[ptrace(2)][ptrace]

**⑥ `Z`：代码已经执行完，系统还保留一份退出结果。**

子进程退出后，父进程可能还没有来得及读取“退出码是多少、是否被信号结束”等信息。在通常的子进程回收规则下，系统会暂时保留必要记录，等待父进程领取。此时它已经不能继续执行自己的业务代码，但仍能在进程表中被看到，状态就是 `Z`，命令名常带 `<defunct>`。[依据：exit(3)][exit]

不要把 `Z` 理解成“暂停以后还能继续”，也不要理解成“操作系统忘记杀它”。保留退出信息有正当用途；真正需要修复的是**大量、长期积累而没有被回收**的僵尸。它与 `wait()`、`waitpid()` 的关系会在 1.4 通过代码展开。

**⑦ `X` 与 `I`：知道含义，不必人为制造。**

`X` 是退出清理中的死亡标记，不是 `exit(0)` 里的数字退出码，正常 `ps` 不应展示它。`I` 常用于空闲内核线程，不是“用户程序只要空闲就变成 I”。例如你自己写的 `sleep_demo` 等待时通常是 `S`，不会因为“很闲”就自动显示为 `I`。[依据：ps(1)][ps]

### 1.2.3 第二张 Linux 状态图、旧源码与两套名字怎样对应

你上传的蓝色 Linux 图，把 `TASK_RUNNING` 和“占有 CPU 执行”画成两个框，是为了教学上区分“有运行资格”和“实际执行”。**它们并不是两种不同的 `ps` 字母状态：这两种情况都可能显示 `R`。**

重组后的阅读图如下：

```text
                        获得 CPU
               ┌──────────────────────┐
               ↓                      │
      正在 CPU 上执行（R）      就绪、等 CPU（R）
               │                      ↑
               ├─ 被抢占/让出 CPU ────┘
               │
               ├─ 等普通事件 ─→ S ── 条件满足/适当信号 ─→ 可运行 R
               │
               ├─ 进入不可中断等待 ─→ D ── 等待条件满足 ─→ 可运行 R
               │
               ├─ 作业控制停止 ─→ T ── 继续 ─→ 恢复后续执行/等待
               │
               ├─ 跟踪、调试暂停 ─→ t ── 调试器恢复 ─→ 后续执行
               │
               └─ 结束执行 ─→ 保留退出信息 Z ── 父进程回收 ─→ 不再可见
```

最后一行描述的是通常的退出与回收流程；父进程立即回收或明确配置自动回收时，不一定能采样到 `Z`。图是理解主线用的，不是列出所有内核瞬时状态和所有特殊信号路径。[依据：内核状态定义][kernel-sched]、[exit(3)][exit]

| 蓝色原图中的箭头或标注 | 应当怎样读 |
|---|---|
| 顶部入口 → `TASK_RUNNING` | 任务进入可运行阶段，不保证立即执行 |
| `TASK_RUNNING` → “占有 CPU”，`schedule()` | 调度器选中任务并使它得到执行机会；`schedule()` 本身不保证每次都换到另一个任务 |
| “占有 CPU” → `TASK_RUNNING`，“时间片耗尽” | 当前停止占用 CPU，但仍具备运行条件，因此依旧可能是 `R` |
| “占有 CPU” → `TASK_INTERRUPTIBLE` | 进入可中断等待，原图用旧的睡眠接口名表达这一过程 |
| `TASK_INTERRUPTIBLE` → `TASK_RUNNING`，`wake_up_interruptible()` / `wake_up()` | 等待条件满足或合适信号使等待改变，任务被唤醒；不等于立刻在 CPU 上运行 |
| “占有 CPU” → `TASK_UNINTERRUPTIBLE` | 进入不可中断等待，不是“执行磁盘程序”的意思 |
| `TASK_UNINTERRUPTIBLE` → `TASK_RUNNING`，`wake_up()` | 等待条件被满足，内核使任务重新可运行 |
| “占有 CPU” → `TASK_STOPPED` | 用一个框概括了暂停；原图同时写 `ptrace()`，实际应区分作业控制停止 `T` 与调试暂停 `t` |
| `TASK_STOPPED` → `TASK_RUNNING`，`SIGCONT` | 对普通作业控制停止，继续信号解除停止；不要套用到所有调试情形 |
| “占有 CPU” → `TASK_ZOMBIE`，`do_exit()` | 内核处理任务退出；图中 `TASK_ZOMBIE` 是旧式或教学标签，本文核对的源码使用 `EXIT_ZOMBIE` |

原图中的“浅度睡眠/深度睡眠”容易让人想到人的睡眠深浅。更准确的读法是“可中断/不可中断等待”，区别在于等待如何受事件和信号影响，不在于睡了多久。图中的 `sleep_on()` 等名字也不要拿来直接写用户态 C 程序：本章应用层实验使用 `sleep()`、`waitpid()` 等接口，旧图只是帮助理解概念。

**截图中的状态字符串代码：**

```c
static const char *const task_state_array[] = {
    "R (running)",      /* 0 */
    "S (sleeping)",     /* 1 */
    "D (disk sleep)",   /* 2 */
    "T (stopped)",      /* 4 */
    "t (tracing stop)", /* 8 */
    "X (dead)",         /* 16 */
    "Z (zombie)",       /* 32 */
};
```

这段代码**不是创建七个进程，也不会使进程逐行变换状态**。它建立的是一张用于显示的字符串表。系统根据任务的状态计算相应索引，再选择合适的文字对外展示。[对照：Linux v6.12 的 fs/proc/array.c][kernel-array]

| 代码部分 | 从零解释 |
|---|---|
| `char` | C 中表示字符的类型；多个字符组成以 `\0` 结尾的 C 字符串 |
| `"R (running)"` | 一个字符串字面量，用来显示文字，不是在执行 `running` 这个动作 |
| `const char *` | 指向字符的指针，通过它不应修改所指向的字符内容 |
| `*const` 中第二个 `const` | 限制这个指针元素本身，不允许把它重新指向另一个字符串 |
| `task_state_array` | 数组名字，可以把数组理解为按位置存放的一组元素 |
| `[]` | 这里没有写长度，编译器会按初始化元素数量确定长度 |
| `{ ... }` | 用这些元素初始化数组 |
| `static` | 在这类文件作用域声明中，使该对象只在当前源文件内被名字直接引用 |
| `/* ... */` | 注释，帮助人阅读，不是程序运行时的操作 |
| 行尾 `,` 与最后 `;` | 逗号分隔元素，分号结束这条声明；最后一个元素后的逗号在这里合法 |

**注释为什么是 `0、1、2、4、8、16、32`，而不是数组下标 `0、1、2、3、4、5、6`？**因为这些注释在说明相应状态的标志值，而不是说“第四个元素的下标是 4”。`1、2、4、8` 分别对应不同二进制位，适合用来记录、组合状态标志。你只需理解“状态标志”和“数组下标”不是同一个编号系统，内核会做转换，不能直接拿 `32` 去访问这个七元素数组。

原注释把它称为一种特殊的 bitmap，即位图/位标志表达。`TASK_RUNNING` 为 0 也不是错误码，而是这里对可运行状态的定义。对于固定的 Linux v6.12 源码，可以看到以下简化对应；实际完整定义还有更多组合标志。[依据：Linux v6.12 include/linux/sched.h][kernel-sched]

```c
#define TASK_RUNNING          0x00000000
#define TASK_INTERRUPTIBLE    0x00000001
#define TASK_UNINTERRUPTIBLE  0x00000002
#define __TASK_STOPPED        0x00000004
#define __TASK_TRACED         0x00000008
#define EXIT_DEAD             0x00000010
#define EXIT_ZOMBIE           0x00000020
```

`#define` 给一个常量值起名字；`0x` 表示后面是十六进制，所以 `0x10` 是十进制 16，`0x20` 是十进制 32。这里展示固定版本是为了便于核对，不是在声称它是你机器上正在运行的版本。

还要知道两点：一是内核把任务的可运行性状态与退出状态分开记录，不能把所有宏都说成“同一个字段里的单选数字”；二是 v6.12 的显示数组还有 `P (parked)`、`I (idle)` 等内容，因此截图只是相关片段，不是所有版本、所有用途下的完整状态清单。初学阶段不用背完整位掩码，把它和 `ps` 能看到的行为联系起来即可。[依据：内核任务状态字段说明][kernel-sched]、[状态显示数组][kernel-array]

## 1.3 不只背字母：读懂 ps 输出，再亲眼观察状态变化

### 1.3.1 ps aux、ps ajx、ps -ef 和 /proc 分别怎么看

**`ps` 是快照工具。**它显示的是读取时获得的进程信息，命令结束后不会自动刷新。它也不是一张冻结所有 CPU 后拍下的绝对同时照片：在它读取不同进程信息期间，进程仍可能继续改变状态。`top`、`watch` 可以反复更新显示，但同样是采样，不是保存每一次瞬时状态转换。[依据：ps(1)][ps]

截图中的 `ps aux / ps axj` 表示两种可选命令，**不要把中间的 `/` 原样作为命令参数输入**。应分别执行：

```bash
ps aux
ps ajx
ps -ef
```

这里 `ps ajx` 和 `ps axj` 都是在组合不带横线的 BSD 风格选项。`ps aux` 不要随意改成 `ps -aux`：带不带横线涉及不同语法传统，后者在部分解释规则下有歧义。[依据：ps(1) 参数语法与兼容性说明][ps]

| 命令/选项 | 选择哪些进程或显示什么 | 初学者容易看错的地方 |
|---|---|---|
| `ps aux` 中的 `a` | 放开 BSD 风格的“只看自己的进程”限制，和 `x` 配合可查看所有进程 | 不只是“当前这个终端里”的进程 |
| `ps aux` 中的 `x` | 放开“必须有控制终端”的限制 | 服务等没有控制终端的进程也能出现 |
| `ps aux` 中的 `u` | 使用偏向用户和资源信息的显示格式 | 这里的 `u` 不是“只选择某个用户名” |
| `ps ajx` 中的 `j` | 使用作业控制格式，显示 PPID、进程组、会话等 | 重点在关系与作业信息，而不是 CPU/内存百分比 |
| `ps -ef` 中的 `-e` | 选择全部进程 | 等价于这一用途下的 `-A` |
| `ps -ef` 中的 `-f` | 完整格式，包括 PID、PPID、启动时间等 | “完整”不表示一定包含 `STAT` 列 |

**`ps aux` 每一列都在说什么？**

```text
USER   PID  %CPU  %MEM   VSZ   RSS  TTY    STAT  START  TIME  COMMAND
root  3872   0.0   0.0  1868   372  pts/0  S+    19:48  0:00  ./test
root  3873   0.0   0.0     0     0  pts/0  Z+    19:48  0:00  [test] <defunct>
```

上面按上传截图中的可见结果重排了格式，用来讲列含义；你机器上的 PID、时间和资源值不会必须相同。

| 列 | 含义 | 怎么使用 |
|---|---|---|
| `USER` | 进程所属用户的显示名称 | 判断是否是自己启动的实验程序 |
| `PID` | 进程编号 | 传给 `ps -p`、`kill` 等进行精确定位 |
| `%CPU` | `ps` 依据累计 CPU 时间与已运行时长等计算的使用比例 | 不是“此刻一定占了多少 CPU”的证明；显示 0.0 也可能只是很小而被舍入 |
| `%MEM` | 常用实现中，常驻内存与机器物理内存的比例 | 用来看大致内存占用，不能单靠它理解所有共享内存关系 |
| `VSZ` | 虚拟内存大小，通常以 KiB 表示 | 不是“实际独占了这么多物理内存” |
| `RSS` | 当前驻留在物理内存中的内存大小，通常以 KiB 表示 | 与 `VSZ` 不是一个概念，也不能把所有进程 RSS 简单相加当作独占内存 |
| `TTY` | 控制终端，`pts/0` 常表示一个伪终端 | `?` 通常表示没有控制终端，不等于故障 |
| `STAT` | 主状态字母及附加属性 | 本章最关注的列 |
| `START` | 启动时刻或日期 | 用来判断大致是什么时候启动的 |
| `TIME` | 累计使用 CPU 的时间 | 不包含全部等待时间，不是“进程已经存在多久” |
| `COMMAND` | 程序名或启动命令及参数 | 帮助识别进程，但不应只靠一个模糊关键字执行破坏性操作 |

这些列的精确定义可查 [ps(1) 的输出字段说明][ps]；内存字段的补充解释见 [/proc/PID/status][proc-status]。例如一个进程存在 30 秒，但大部分时间在睡眠，累计 CPU 时间仍可能显示 `0:00`，两者并不矛盾。

**`S+`、`Ss`、`Sl` 是不是新的状态？**不是。通常先看第一个状态字符，再看后面的附加属性。

| 属性 | 含义 | 例子 |
|---|---|---|
| `+` | 属于终端的前台进程组 | `S+`：正在睡眠，而且属于前台进程组 |
| 小写 `s` | 会话首进程 | `Ss`：可中断睡眠，同时是会话首进程 |
| 小写 `l` | 多线程 | `Sl`：相应任务状态为 S，且进程为多线程 |
| `<` | 较高调度优先级的标记 | 不是小于号比较表达式 |
| `N` | 较低调度优先级的标记 | 常与较大的 nice 值有关 |
| `L` | 有内存页被锁定在内存中 | 不等于线程程序里“拿到了一把互斥锁” |

注意区分大写 `S` 与后缀小写 `s`、大写 `T` 与独立状态小写 `t`。`Z+` 也不矛盾：`Z` 表示已退出待回收，`+` 描述它仍记录的进程组与终端关系，**不代表僵尸仍在前台执行代码**。[依据：ps(1) 的附加状态字符][ps]

截图中 `[test] <defunct>` 表示该进程已经失去正常可执行的进程形态而处于僵尸状态。`<defunct>` 是状态提示，不是你起的源文件名；截图窄时它被折成两行，也不是多出了一个进程。僵尸行的 `VSZ/RSS` 可能为 0，但保留退出记录仍占内核管理资源，所以不能据此说“僵尸完全不占任何资源”。[依据：ps(1)][ps]、[exit(3)][exit]

**`ps ajx` 为什么适合看父子关系？**因为它通常把这些列放出来：

```text
PPID   PID   PGID   SID  TTY    TPGID  STAT  UID  TIME  COMMAND
2000  3000   3000  2000  pts/0   3000  S+   1000 0:00  ./test
3000  3001   3000  2000  pts/0   3000  Z+   1000 0:00  [test] <defunct>
```

这是说明列关系的示意输出。`PPID` 是父进程编号，`PID` 是自身编号；`PGID` 是进程组编号，一组进程可以作为一个作业整体接受前后台控制；`SID` 是会话编号，表示更大一层的终端/进程组组织关系；`TPGID` 是相应终端当前前台进程组编号；`UID` 是用户的数字标识，和以名字显示的 `USER` 有联系。[依据：ps(1)][ps]、[进程凭据与进程组说明][credentials]

在上面，3001 的父进程是 3000，两者同属 3000 这个进程组。一个新子进程并不意味着自动新建一个会话或进程组。因此你看孤儿实验时，应重点观察 **PPID 是否改变**，不是要求 PGID、SID 都跟着改变。

**`ps -ef` 的典型表头：**

```text
UID  PID  PPID  C  STIME  TTY  TIME  CMD
```

其中 `UID` 在该格式下可能显示用户名，`C` 是 CPU 使用情况的整数形式字段，`STIME` 是启动时间，其他主要字段与前面类似。`ps aux` 与 `ps -ef` 都常被用来查看广泛的进程集合，但默认输出列不同。**要观察状态，不能因为使用了 `ps -ef` 就假定一定有 `STAT`；直接指定需要的列更清楚。**[依据：ps(1)][ps]

```bash
ps -p 3873 -o pid,ppid,stat,etime,time,comm
```

`-p 3873` 只选择 PID 为 3873 的进程，实际使用时换成你刚查到的 PID；`-o` 指定输出格式，逗号分隔列；`etime` 是启动以来经过的现实时间，`time` 是累计 CPU 时间，`comm` 是命令名。只显示表头通常表示没有选到当前存在的目标，可能是 PID 填错，也可能是进程已经被回收。

**`/proc` 又是什么？**`/proc` 是内核向用户空间提供信息的虚拟文件系统，其中 `/proc/3873/status` 可以展示进程的状态等内容。读取它，不是打开源代码，也不是读取“进程以前保存下来的日志”。进程变化后，下次读取的结果可能变化；进程最终消失后，相应目录也会消失。[依据：proc_pid_status(5)][proc-status]

```bash
cat /proc/3873/status
```

`cat` 把文件内容输出到终端。你可以重点找：

```text
Name:   test
State:  Z (zombie)
Pid:    3873
PPid:   3872
```

`Name` 是名称，`State` 是状态，`Pid` 是自身编号，`PPid` 是父进程编号。用这四行就能交叉验证“哪个进程、属于谁、现在是什么状态”。这里的数字仅对应前面的说明例子。

### 1.3.2 筛选、持续观察与最小 R/S 实验

**先理解截图中的管道筛选：**

```bash
ps aux | grep test | grep -v grep
```

执行顺序是：`ps aux` 产生多行文本；第一个 `|` 把它的标准输出交给 `grep test`；`grep test` 保留包含 `test` 的行；第二个管道把这些行交给 `grep -v grep`，后者排除含 `grep` 的行。`grep` 在这里是在筛选文本，不是在改变进程状态。[依据：Bash 管道][bash]、[grep(1)][grep]

为什么经常要排除 `grep`？因为正在执行的 `grep test` 自己也可能出现在 `ps` 的结果里，而且命令行中包含 `test`。但这种排除方式并不完美：真正目标命令行里如果也含 `grep`，也可能被误删。更稳妥的入门方法是按命令名或已知 PID 查询：

```bash
ps -C sleep_demo -o pid,ppid,stat,etime,time,comm
pgrep -ax sleep_demo
```

`ps -C` 按命令名选择；`pgrep` 用来搜索进程，`-x` 要求名称精确匹配，`-a` 同时显示完整命令行。注意，不同命令里的同一个字母参数不一定同义，`pgrep -a` 不能套用 `ps a` 的解释。[依据：ps(1)][ps]、[pgrep(1)][pgrep]

**截图中循环监控命令的意思：**

```bash
while :; do
    ps aux | grep test | grep -v grep
    sleep 1
    echo '################'
done
```

`while 条件; do ... done` 表示条件成立就反复执行循环体；`:` 是一个返回成功的 Shell 内置命令，因此条件一直成立；`sleep 1` 每轮等待一秒，避免无休止地快速刷屏；`echo` 打印分隔线。这里的 Shell 命令 `sleep 1` 和 C 里的 `sleep(1)` 写法不同，但都用于表达等待一段时间。按 `Ctrl+C` 可以停止当前前台的监控循环。[依据：Bash 命令语法][bash]

也可以用更短的监控命令：

```bash
watch -n 0.5 'ps -C sleep_demo -o pid,ppid,stat,etime,time,comm'
```

`watch` 每隔指定时间重新执行命令；`-n 0.5` 表示间隔约 0.5 秒；单引号把内部整条命令作为一个参数交给 `watch`。它仍是间隔采样，不保证捕获所有短暂状态；退出用 `Ctrl+C`。[依据：watch(1)][watch]

`top -p 3873` 可以持续查看指定进程，交互界面里通常用 `q` 退出；`pstree -p` 以树状结构显示进程及 PID，更适合看父子关系，而不是精确替代 `ps` 的状态列。命令不存在时是工具未安装或不在 PATH 中，并不自动意味着程序有问题。[依据：top(1)][top]、[pstree(1)][pstree]

**准备两个连接同一台 Linux 的终端。**终端 A 用来编译、运行程序，终端 B 用来观察。前台程序占着终端 A 时，你不能把随后输入的 `ps` 当作一定会被 Shell 执行；Shell 可能正在等前台程序结束，而输入会交给前台程序。

在终端 A 建立独立实验目录，避免改动已有文件：

```bash
mkdir -p ~/linux_process_state_lab
cd ~/linux_process_state_lab
gcc --version
```

`~` 代表当前用户家目录；`mkdir -p` 创建目录，目录已存在时不因此报错；`cd` 切换当前工作目录。`gcc --version` 检查编译器是否可用。以下文件可以在 VS Code 中创建，也可以从附带的代码包复制；保存为 `.c` 文件，不能把 Markdown 的三反引号一并保存进去。

**实验 A：用忙循环观察 `R`。文件名：`busy_demo.c`。**

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("busy process: PID=%ld\n", (long)getpid());
    fflush(stdout);
    while (1) {
        /* 故意不睡眠：仅用于短时间观察 R，实验后按 Ctrl+C。 */
    }
}
```

`#include <stdio.h>` 提供输出函数声明，`#include <unistd.h>` 提供本例所用的 `getpid()` 等 POSIX 接口声明。`int main(void)` 是程序入口：返回类型是整数，`void` 表示这里不接收参数。`printf()` 输出一行文字；`%ld` 表示按 `long` 整数打印，`(long)getpid()` 是把 PID 转成与格式匹配的类型；`\n` 是换行。

`fflush(stdout)` 把标准输出缓冲区里暂存的内容交给底层输出，确保开始实验的信息及时出现。特别是输出被重定向到文件时，不能仅凭 `printf()` 已执行就假定马上能在文件里看到它。`stdout` 是标准输出流，不是文件名。[依据：fflush(3)][fflush]

`while (1)` 表示条件始终为真，反复执行大括号中的循环体。本例循环体故意不调用等待接口，即使里面没有业务操作，CPU 仍在执行循环控制等机器指令。这是有意写的短时教学忙循环，不是正常业务程序的推荐写法。

```bash
# 终端 A：编译并运行
gcc -std=c11 -Wall -Wextra -O0 busy_demo.c -o busy_demo
./busy_demo
```

`gcc` 是编译器；`-std=c11` 按 C11 语言标准编译；`-Wall -Wextra` 开启常用及额外警告；`-O0` 中最后一个是数字 0，表示关闭优化，便于学习观察；`-o busy_demo` 指定输出的可执行文件名称。编译不等于运行，编译成功后输入 `./busy_demo` 才启动程序；`./` 表示当前目录。[依据：GCC 命令选项][gcc-options]、[GCC 警告选项][gcc-warning]、[GCC 优化选项][gcc-opt]

```bash
# 终端 B：观察
ps -C busy_demo -o pid,ppid,stat,pcpu,time,comm
```

`pcpu` 是 CPU 使用比例字段。你通常会看到 `R` 或 `R+`；`+` 是否出现取决于启动方式和终端关系，而不是是否真的创建了进程。忙循环会消耗 CPU，观察几秒钟后，回终端 A 按 `Ctrl+C` 结束，不要开很多份长期运行。

**实验 B：每秒打印一次，观察为什么通常显示 `S`。文件名：`sleep_demo.c`。**

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    while (1) {
        printf("I am alive: PID=%ld\n", (long)getpid());
        fflush(stdout);
        sleep(1);
    }
}
```

与上一程序相比，这次循环中有 `sleep(1)`：每一轮先输出，再暂停当前线程约一秒。睡眠结束只代表可以继续参加调度，不保证下一行恰好在一秒整执行；系统负载、调度和信号都会影响实际观察时刻。[依据：sleep(3)][sleep]

```bash
# 终端 A
gcc -std=c11 -Wall -Wextra -O0 sleep_demo.c -o sleep_demo
./sleep_demo
```

```bash
# 终端 B
watch -n 0.5 'ps -C sleep_demo -o pid,ppid,stat,pcpu,time,comm'
```

你会看到终端 A 不断输出，而终端 B 多数时候显示 `S` 或 `S+`。这恰好验证了“仍然活着并定期工作”和“采样时正在睡眠”可以同时成立。结束时先在终端 B 按 `Ctrl+C` 退出监控，再到终端 A 按 `Ctrl+C` 结束程序，别把两个动作混在一起。

**不写 C 也能观察正常等待：**在终端 A 运行 `cat`，暂时不输入内容；在终端 B 查询 `ps -C cat -o pid,ppid,stat,comm`，通常能看到它在等待输入。回到终端 A 输入一行并回车，`cat` 会把它输出；空行起始处按 `Ctrl+D` 可以向程序表现为输入结束。这个例子说明睡眠/等待不只来自显式的 `sleep()`。[依据：终端控制][termios]、[cat(1)][cat]

**为什么没有安排“制造 D 状态”的实验？**因为本章的目标是理解状态，而不是通过破坏设备或人为制造存储故障来观察一个字母。`R/S/T/Z` 和父子进程回收能用很小的程序安全验证；`D` 则优先通过官方定义和真实故障排查资料理解。

## 1.4 从 fork 到退出：把僵尸、孤儿和 wait 用代码串起来

### 1.4.1 先解决代码阅读障碍：fork 为什么会走出两条执行路线

截图里的核心语句是：

```c
pid_t id = fork();
```

把它拆成三部分看：`pid_t` 是适合保存进程 ID 的类型；`id` 是你自己起的变量名，也可以叫 `pid`；`fork()` 请求创建一个子进程，并把返回值赋给变量。**变量名叫 `id`，并不意味着它永远保存“当前进程自己的 PID”。**它存的是这次 `fork()` 在当前执行流中的返回值。

| 当前情况 | `fork()` 返回值 | `id` 在这条执行流中表示什么 |
|---|---|---|
| 创建失败 | `-1` | 失败标记，没有成功创建这次请求的子进程 |
| 创建成功，当前在父进程中 | 子进程的 PID，大于 0 | 父进程通过这个值知道新子进程是谁 |
| 创建成功，当前在子进程中 | `0` | 告诉新执行流“你是这次 fork 出来的子进程” |

成功后，父子进程都从 `fork()` 返回的位置继续，不是子进程重新从源文件第一行执行，也不是同一个进程把后续代码执行两遍。“调用一次、成功后有两条返回路线”才是更准确的入门理解。[依据：fork(2)][fork]

```text
fork 前：只有父进程 P，PID=3000
                     │
                  fork()
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
父进程 P，PID=3000      子进程 C，PID=3001
id=3001                id=0
继续执行后面的判断       也继续执行同一个位置后面的判断
```

因此，截图常写成下面这样。它是解释控制流的片段，完整程序在下一小节：

```c
if (id < 0) {
    /* 创建失败 */
} else if (id > 0) {
    /* 只有父进程进入这里 */
} else {
    /* 前两种情况都不成立，只剩 id == 0，即子进程 */
}
```

`if` 是“如果”；`else if` 是“前一个条件不成立，再判断”；`else` 是“前面的条件都不成立，走这里”。**同一条执行流只会进入其中一支，但父子进程会各自判断一遍。**父进程看到自己的 `id > 0`，进入父分支；子进程看到自己的 `id == 0`，进入子分支。

`=` 是赋值，`==` 才是比较。`if (id = 0)` 会把 `id` 改成 0，再根据这个结果判断，和“判断 id 是否等于 0”不是一回事。代码中的 `id < 0` 或 `id == -1` 都可用于检查 `fork()` 的失败返回，但不要把成功子进程里的 0 当成失败。

**为什么同一个变量会有两个值？**因为父子是两个进程，通常有相互隔离的私有地址空间。成功返回后，它们各自保存自己的返回结果。Linux 通常利用写时复制（Copy-on-Write，COW）避免在创建时立刻复制所有私有内存数据；需要产生私有副本时按内存页处理，不是只复制“被修改的那一个 C 变量”。本章只需要记住：子进程修改普通私有变量，通常不会自动改到父进程里的那份变量。[依据：fork(2) 的内存语义与 Linux 实现说明][fork]

**父分支先执行，还是子分支先执行？**没有普遍保证。源代码把父分支写在上面，只说明代码如何排版，不是在给调度器规定顺序。你看到父进程先输出或子进程先输出，都可能正常；需要严格依赖先后关系时，应使用等待、管道等同步机制，而不是“我连续跑了几次都是这个顺序”。

**这些基础函数和语法，先在这里统一认清：**

| 写法 | 作用 | 常见误会 |
|---|---|---|
| `getpid()` | 查询当前执行者自己的 PID | 子进程的 `id` 为 0，不等于它真正的 PID 是 0 |
| `getppid()` | 查询当前父进程的 PID | 不能用一次查询值代表永远不变的父关系 |
| `sleep(5)` | 当前线程等待一段时间 | 不是让所有进程都睡，也不是等待某个子进程 |
| `printf(...)` | 按格式输出文字 | 输出出现的顺序不一定等于源代码中分支的书写顺序 |
| `perror("fork")` | 输出前缀及当前错误原因，通常写到标准错误 | 不是创建失败的原因本身，而是报告已经发生的错误 |
| `return 1` | 在 `main` 中返回非零状态，表示本程序按约定报告失败 | 不会再顺着执行后面的 `return 0` |
| `exit(0)` | 结束当前进程，按通常约定报告成功 | 不是“退出 if 分支”，也不会继续执行它后面的普通语句 |
| `EXIT_SUCCESS` | 标准库提供的成功状态常量，在常见 Linux 环境中是 0 | 不是进程状态 `R/S/Z` 之一 |
| `EXIT_FAILURE` | 标准库提供的失败状态常量 | 不需要为了学习把所有失败都硬编码为同一个具体数字 |

接口与错误输出说明见 [getpid(2)][getpid]、[sleep(3)][sleep]、[perror(3)][perror]、[exit(3)][exit]。后面重复出现的这些语法会直接使用，不再每次重抄整张表。

### 1.4.2 僵尸进程：退出不等于“所有痕迹同一瞬间消失”

先区分三个不同动作：

```text
结束执行：这个进程不再运行自己的代码。
释放大部分执行资源：例如退出时释放自己的地址空间、关闭自己的文件描述符等。
回收退出记录：父进程取得退出信息后，系统完成剩余进程记录的回收。
```

这些动作相关，但不能合并成一句“进程退出了，就一切都没有了”。在通常的回收规则下，系统会保留子进程 PID、终止状态和必要资源统计，便于父进程稍后知道“它是否完成、怎样退出”。**保留退出记录期间，子进程不再是一个继续运行业务的执行者，却还可能作为 `Z` 出现在 `ps` 中。**[依据：exit(3)][exit]、[_exit(2)][_exit]

为什么要保存退出码？例如父进程把文件转换任务交给子进程，子进程可能成功、找不到输入文件，或者处理中被信号结束。父进程要知道结果，才能决定下一步是处理成品、重试，还是报告错误。保留退出状态相当于保存一张“完成结果”，不是为了让已结束的代码重新运行。

**`exit(0)` 以后，后面那句还能执行吗？**

```c
exit(0);
printf("this line will not run\n");
```

正常情况下不会。`exit()` 不返回到调用点；这里结束的是调用它的当前进程。在子分支调用 `exit()`，不会因此把独立的父进程也一起结束。父进程是否继续，取决于父进程自己的控制流和系统的其他管理策略。[依据：exit(3)][exit]

**`return 0` 和 `exit(0)` 有什么区别？**在通常的 C 程序中，从最初的 `main()` 返回 0，会进入正常进程终止流程；而在普通自定义函数里 `return 0`，只是把数值 0 返回给调用者，进程可以继续。`exit(0)` 无论从普通函数还是从 `main()` 调用，都请求结束当前进程。另有 `_exit()`，它跳过 `exit()` 的一些 C 库清理，例如不刷新标准 I/O 缓冲区；本章示例主要使用 `exit()`，不能在没理解输出缓冲的情况下随意替换。[依据：exit(3)][exit]、[_exit(2)][_exit]、[C11 main 返回语义][c-standard]

**子进程修改过的东西会不会都没意义？**普通私有变量在子进程退出后不再作为这个进程的工作内存继续存在，也不会自动变成父进程变量；但它输出到终端的内容、成功写出的文件、通过管道发送的数据，可能已经产生外部效果。`waitpid()` 取得的是退出结果，不会把子进程的普通变量整份复制回父进程。子进程的意义在于完成工作或产生可观察结果，不在于必须永久存在。

**把截图中的僵尸示例补成完整程序。文件名：`zombie_original.c`。**下面按可见逻辑重建：父进程睡 30 秒，子进程睡 5 秒后退出，父进程不调用 `wait()`。原截图存在缺失的头文件和被遮挡的输出行，这里补齐声明、重写提示文字，不把看不到的部分伪称为逐字原文。

```c
/* 根据截图中可见逻辑重建，不是被遮挡代码的逐字转录。
 * 故意不回收子进程，用于解释原图；日常实验优先用 zombie_demo.c。
 */
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>

int main(void)
{
    pid_t id = fork();
    if (id < 0) {
        perror("fork");
        return 1;
    } else if (id > 0) {
        printf("parent[%ld] is sleeping...\n", (long)getpid());
        fflush(stdout);
        sleep(30);
    } else {
        printf("child[%ld] will exit after 5 seconds\n", (long)getpid());
        fflush(stdout);
        sleep(5);
        exit(EXIT_SUCCESS);
    }
    return 0;
}
```

先沿每一条执行路线阅读，而不是把整个文件从上到下只当成“一条线”：

| 位置 | 父进程做什么 | 子进程做什么 |
|---|---|---|
| `pid_t id = fork();` | 获得子进程 PID | 获得 0 |
| `if (id < 0)` | 成功时跳过失败分支 | 成功时也跳过失败分支 |
| `else if (id > 0)` | 条件成立，进入父分支 | 条件不成立，进入后面的 `else` |
| `printf()`、`fflush()` | 打印自己的提示 | 打印自己的提示 |
| `sleep(...)` | 等约 30 秒 | 等约 5 秒 |
| 子分支 `exit(EXIT_SUCCESS)` | 不执行这一句 | 结束执行，留下待领取的退出信息 |
| 文件末尾 `return 0` | 30 秒后走到这里，父进程结束 | 已经在 `exit()` 结束，不再走到这里 |

`<sys/types.h>` 提供 `pid_t` 等类型的声明，`<stdlib.h>` 提供 `exit()` 和成功/失败常量，`<unistd.h>` 提供 `fork()`、`sleep()` 等接口。原截图仅靠少量头文件的写法不要原封不动照搬；现代编译器警告缺少函数声明时，应补正确头文件，而不是关闭警告。

**按常见调度情况看时间线：**

| 大约时间 | 父进程 | 子进程 | 你应当理解什么 |
|---|---|---|---|
| 开始 | 执行 `fork()`，随后输出 | 从 `fork()` 返回后输出 | 有了两条执行流，输出先后不保证 |
| 0～5 秒 | 多数时间在 `sleep(30)`，通常 S | 多数时间在 `sleep(5)`，通常 S | 两个进程都还没结束 |
| 约 5 秒 | 仍在睡眠，没有回收 | 执行 `exit()`，随后成为 Z | 子进程已经不再执行自己的代码 |
| 约 5～30 秒 | 仍存在，未调用等待回收接口 | 退出记录还在，能够被 `ps` 看见 | 这是观察僵尸的主要窗口 |
| 约 30 秒 | `main` 返回，父进程退出 | 原父关系结束，遗留退出记录交给收养者处理 | 是否立即消失取决于收养者是否及时回收 |

**原资料说“维持 30 秒的僵尸”，这个说法需要修正。**若父进程从开始睡 30 秒、子进程从开始睡 5 秒，通常可观察的僵尸窗口约为 `30 - 5 = 25` 秒，而不是子进程整个生命周期都处于 Z。实际时间还受调度、信号和启动先后影响；`sleep()` 是为了扩大观察窗口，不是精确同步工具。

截图里父进程一行是 `S+`、子进程一行是 `Z+`，正对应时间线中间的阶段。父进程也不是在“替子进程运行”，它只是在自己的 `sleep(30)` 中等时间；子进程的退出记录则由内核保存。

**只运行一次即可观察，不要批量制造僵尸。**`zombie_original.c` 故意没有回收逻辑，只用于对照原截图；在不负责回收后代的容器环境中，遗留记录可能持续存在。首次动手建议直接使用下面的版本，等它完成收尾，不要提前杀掉父进程。

**实际动手优先用会收尾的版本。文件名：`zombie_demo.c`。**它保留同样的观察窗口，但父进程最后主动回收，不把遗留记录完全交给环境中的 PID 1。新增的 `waitpid()` 在下一小节会拆开详细解释。

```c
/* 保留父睡 30 秒、子睡 5 秒的观察窗口，最后由父进程主动回收。 */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return EXIT_FAILURE;
    }

    if (pid == 0) {
        printf("child: PID=%ld, PPID=%ld; exit in 5 seconds\n",
               (long)getpid(), (long)getppid());
        fflush(stdout);
        sleep(5);
        exit(EXIT_SUCCESS);
    }

    printf("parent: PID=%ld, child PID=%ld; wait in 30 seconds\n",
           (long)getpid(), (long)pid);
    fflush(stdout);
    sleep(30);

    pid_t result;
    do {
        result = waitpid(pid, NULL, 0);
    } while (result == -1 && errno == EINTR);

    if (result == -1) {
        perror("waitpid");
        return EXIT_FAILURE;
    }
    printf("parent: reaped child PID=%ld\n", (long)result);
    return EXIT_SUCCESS;
}
```

运行约 5 秒后，应能在父进程仍存在时看到子进程为 `Z`；约 30 秒后，父进程调用 `waitpid()` 回收子进程并输出提示，接着自己也退出。终端 B 可能只剩表头。没有看到 Z 时，先检查是否观察太晚、是否运行了另一个文件、是否按错了程序名，不要先认定操作系统不支持僵尸。

这个版本中 `if (pid == 0)` 后面没有 `else`，为什么父进程代码不会被子进程继续执行？因为子进程已经在分支内调用 `exit()` 结束了。父进程没有进入这个分支，所以才会执行下方的父进程逻辑。**把子分支的 `exit()` 删掉，会改变整个程序控制流，不能当作无关紧要的清理语句。**

**僵尸到底占什么，危害是什么？**它已经释放了大部分正常执行资源，不会继续做自己的计算，但仍占据必要的内核管理记录和可用进程标识/表项资源。少量短暂 Z 是正常生命周期可能出现的现象；大量、持续增长的 Z 会使管理资源被占用，严重时无法再正常创建进程。把它笼统说成“整个子进程的堆、栈、内存一直全部保留，发生普通堆内存泄漏”是不准确的。[依据：wait(2) 的僵尸资源说明][wait]

**为什么直接 `kill -9` 一个僵尸没有解决问题？**因为它已经终止，没有还能执行的业务流程供信号再终止一次。缺的是父进程/收养者的回收，不是再发送一遍终止请求。看到大量 Z 时，应先查其 PPID、定位负责回收的程序，再修复等待逻辑；生产环境里不能直接把“杀父进程”当作无风险的通用方案。

### 1.4.3 wait / waitpid：谁等待谁，返回值与退出码又有什么区别

**`wait()` 的本质不是“随便睡一会儿”，而是等待并领取子进程的状态。**对一个已经退出、尚未回收的子进程执行相应等待，会取得退出信息并完成回收；若目标子进程还没结束，普通阻塞等待就让调用者先停在这里，而目标子进程继续自己的执行。[依据：wait(2)][wait]

```text
父进程：fork → waitpid 等待 ─────────────────→ 得到结果，继续父进程代码
                    ↑                             ↑
                    │                     子进程结束，状态可领取
子进程：           获得执行机会 → 做自己的工作 → exit
```

因此，父进程在 `waitpid()` 中等待时通常可显示为 `S`，子进程做计算时可显示为 `R`，子进程自己调用 `sleep()` 时也可显示为 `S`。父进程等待子进程，不等于子进程也要等父进程，更不是两个进程自动陷入死锁。

先看两个常用函数原型：

```c
pid_t wait(int *status);
pid_t waitpid(pid_t pid, int *status, int options);
```

原型是在说明“函数叫什么、接受什么参数、返回什么类型”，不是让你把这两行当成必须再实现一遍的函数。`<sys/wait.h>` 中提供相应声明和状态解析宏。使用者调用这些接口，不需要自己编写内核回收代码。

| 调用 | 含义 |
|---|---|
| `wait(&status)` | 等待任意一个符合条件的子进程，取得其终止状态 |
| `wait(NULL)` | 仍然等待、仍然回收，但不要求把终止状态写入一个变量 |
| `waitpid(pid, &status, 0)`，其中 `pid > 0` | 等待 PID 正好等于 `pid` 的那个子进程 |
| `waitpid(-1, &status, 0)` | 就本章关注的退出等待而言，等价于 `wait(&status)` |
| `waitpid(pid, &status, WNOHANG)` | 查看指定子进程现在是否已经退出；没有退出就立即返回，不在这个调用中一直等 |

默认的 `waitpid(..., 0)` 等待终止；等待系列还能够配合选项报告停止或继续等变化，那不等于每次都在回收一个已终止进程。本章先掌握默认退出回收和 `WNOHANG`，不要把所有“状态变化通知”混称为“僵尸回收”。[依据：wait(2) 的选择与选项][wait]

**把最常见的一句彻底拆开：**

```c
int status = 0;
pid_t result = waitpid(pid, &status, 0);
```

| 部分 | 它到底是什么 |
|---|---|
| `pid` | 输入：父进程想等待哪个子进程，这里用 `fork()` 返回的子进程 PID |
| `status` | 父进程定义的普通整数变量，准备用来接收编码后的状态信息 |
| `&status` | 把这个变量的内存地址传给函数，让函数知道把结果写在哪里 |
| 最后一个 `0` | 输入：没有启用额外选项，使用默认等待行为；它不是子进程退出码 |
| `result` | 函数返回值：成功时告诉你这次领取了哪个子进程的状态 |

**一个函数为什么能给两个结果？**`waitpid()` 通过 C 函数返回值告诉你“这次操作是否成功、对应哪个 PID”，再通过 `&status` 指向的位置写入“那个子进程怎样结束”。这是一种常见的 C 接口设计。你传递的是变量地址，不是让 `waitpid()` 再创建一个叫 `status` 的子进程。

`&status` 中的 `&` 是 C 语言的取地址运算符；Shell 中行末的 `&` 表示后台执行；重定向 `2>&1` 中的 `&` 又属于另一种语法。它们长得一样，但处于不同语言与上下文，不能互相套用。

**`waitpid()` 返回值的三种情况：**

| 返回值 | 对本章默认退出观察的含义 | 能不能解析这次的 `status` |
|---|---|---|
| 大于 0 | 得到一个目标子进程的状态，返回值是它的 PID | 可以，进一步按状态类型判断 |
| 等于 0 | 使用 `WNOHANG`，符合选择条件的子进程还没有可返回的退出状态 | 不应当把这个变量当作已经取得了子进程结果 |
| 等于 -1 | 调用失败，需查看 `errno` | 不应解析为成功结果 |

**这里的 0 不代表“子进程成功退出”。**只有在确实拿到子进程终止状态以后，再解析出退出码 0，才是那一层的“按程序约定成功”。`fork()` 返回的 0、`waitpid()` 配合 `WNOHANG` 返回的 0、`exit(0)` 的 0，是三种不同语境。[依据：wait(2) 返回值说明][wait]

**为什么不能直接 `printf("%d", status)` 就说这是退出码？**因为 `status` 是编码后的信息，其中可能记录“正常退出还是被信号结束、具体退出码或信号是什么”等。应使用匹配的宏来解读：

| 宏 | 用途 | 使用条件 |
|---|---|---|
| `WIFEXITED(status)` | 判断是否经正常退出路径结束 | 成功取得状态后先判断 |
| `WEXITSTATUS(status)` | 提取正常退出码 | 只有 `WIFEXITED(status)` 为真时才这样取 |
| `WIFSIGNALED(status)` | 判断是否被信号终止 | 成功取得状态后判断 |
| `WTERMSIG(status)` | 取得导致终止的信号编号 | 只有 `WIFSIGNALED(status)` 为真时才这样取 |

这里“正常退出路径”不等于“业务成功”。`exit(7)` 也属于正常退出路径，只是退出码是 7，而不是通常表示成功的 0。至于 7 表示什么，由程序约定；本章故意用它展示“父进程确实拿到了子进程给的值”。[依据：wait(2) 状态解析宏][wait]

**完整实验：立即等待并读取退出码。文件名：`wait_demo.c`。**

```c
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return EXIT_FAILURE;
    }

    if (pid == 0) {
        printf("child: PID=%ld; exit(7) in 5 seconds\n", (long)getpid());
        fflush(stdout);
        sleep(5);
        exit(7);
    }

    printf("parent: PID=%ld; waiting for child PID=%ld\n",
           (long)getpid(), (long)pid);
    fflush(stdout);

    int status = 0;
    pid_t result;
    do {
        result = waitpid(pid, &status, 0);
    } while (result == -1 && errno == EINTR);

    if (result == -1) {
        perror("waitpid");
        return EXIT_FAILURE;
    }
    printf("waitpid returned PID=%ld\n", (long)result);
    if (WIFEXITED(status)) {
        printf("child exit code=%d\n", WEXITSTATUS(status));
    } else if (WIFSIGNALED(status)) {
        printf("child killed by signal=%d\n", WTERMSIG(status));
    }
    return EXIT_SUCCESS;
}
```

这个程序最重要的执行关系如下：

```text
子进程：输出 PID → sleep(5) → exit(7)
父进程：输出 PID → waitpid(...) 等待 → 拿到子进程 PID 与状态 → 打印退出码
```

前半段创建与分支的意思和前例相同。新增的 `int status = 0` 准备一块结果存储；`pid_t result` 保存等待接口的返回值。`do { ... } while (...)` 表示先执行一次循环体，然后再检查是否重复，这样 `waitpid()` 至少调用一次。

**为什么错误处理不是简单写一句 `waitpid()` 就完事？**在某些信号处理情况下，阻塞等待可能被打断，此时函数失败返回 `-1`，并把错误原因记为 `EINTR`。这通常不意味着子进程没有了，而是“这次等待被中断，可以重新等待”。因此：

```c
} while (result == -1 && errno == EINTR);
```

这句只在“函数失败”并且“失败原因是被信号中断”时重试。`&&` 表示两个条件都要成立；`errno` 是供程序读取调用失败原因的错误编号，`EINTR` 是其中一种错误常量，声明来自 `<errno.h>`。成功时不要靠旧的 `errno` 判断这次调用是否失败，因为它可能仍保留先前的值。[依据：wait(2) 错误说明][wait]、[errno(3)][errno]

循环结束以后，若仍为 `-1`，说明遇到了其他失败，程序通过 `perror("waitpid")` 报告；如果成功，则先检查是否正常退出，再提取退出码。`WIFSIGNALED()` 分支是为了让你明确：子进程也可能被信号终止，不是所有结束都有一个可按 `WEXITSTATUS()` 理解的业务退出码。

一种可能的输出如下，PID 和前两行顺序仅作示意：

```text

child: PID=4001; exit(7) in 5 seconds
waitpid returned PID=4001
child exit code=7
```

这里 `waitpid returned PID=4001` 与 `child exit code=7` 是两个不同结果。父进程自己最后返回 `EXIT_SUCCESS`，所以随后 Shell 的 `echo $?` 通常打印 **0**，不是 7。`$?` 表示 Shell 最近执行的命令/相应作业的退出状态；这里 Shell 直接启动并等待的是父进程运行的 `./wait_demo`，不是让 `$?` 自动钻进去变成子进程的退出码。[依据：Bash 退出状态与特殊参数][bash]

父进程已经在及时等待，所以通常观察不到长时间停留的子进程 Z；这不意味着 `exit()` 与回收是同一个动作，而是两步衔接得很快。等待接口返回以后，子进程的普通私有变量也不会自动复制到父进程中。

**`wait(NULL)` 会不会因为不保存退出码而不回收？**不会。`NULL` 表示不要求写入状态变量，不表示“不执行回收”。**`wait()` 会不会收走任意人的进程？**通常不会，它针对调用者的子进程/依法收养后的相应关系。新开一个无关终端，不能仅知道某个僵尸 PID，就直接把它当成自己的子进程来 `waitpid()`。[依据：wait(2)][wait]

### 1.4.4 孤儿进程：父进程先结束，子进程不一定跟着结束

**僵尸在讲“子进程已经结束但尚未回收”，孤儿在讲“原父进程先结束”。**通常所说的孤儿进程，是原父进程退出后仍存活的子进程。它可以继续执行、睡眠或等待；“孤儿”不是一个与 `R/S/D/T/Z` 并排的新状态字母。

```text
原来：Bash → 父进程 P → 子进程 C

P 退出以后：
Bash 继续自己的工作
合适的收养者 → C 继续存活；C 的 PID 不变，PPID 改成新父进程
```

Linux 会把失去原父关系的子进程交给适当的收养者。可能是最近的、设置为子进程收割者的祖先进程（subreaper）；没有这样的收养者时，通常由相应 PID 命名空间中的 init/PID 1 接管。这个 PID 1 不必在所有环境中都叫 `systemd`，所以不要把“孤儿的 PPID 必然是 1，而且必须由 systemd 接管”写成无条件规则。[依据：PR_SET_CHILD_SUBREAPER][subreaper]、[_exit(2)][_exit]

`subreaper` 可以先理解为“某个祖先进程向系统登记：后代中间父进程退出时，我愿意接手它们并负责回收”。它不是系统随机选的任何一个进程。容器、服务管理和测试环境可能安排这样的收养者；本章不要求你现在编写它，只需要知道观察到非 1 的新 PPID 不必然是错误。

**截图的原始孤儿逻辑。文件名：`orphan_original.c`。**

```c
/* 按截图结构重排，补充类型头文件、可移植的 PID 输出与输出刷新。 */
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>

int main(void)
{
    pid_t id = fork();
    if (id < 0) {
        perror("fork");
        return 1;
    } else if (id == 0) {
        printf("I am child, pid: %ld\n", (long)getpid());
        fflush(stdout);
        sleep(10);
    } else {
        printf("I am parent, pid: %ld\n", (long)getpid());
        fflush(stdout);
        sleep(3);
        exit(0);
    }
    return 0;
}
```

父进程进入 `else`，打印后睡约 3 秒，再 `exit(0)`；子进程进入 `id == 0` 分支，打印后睡约 10 秒，随后走到末尾 `return 0`。因此在通常启动顺序下，大约第 3 秒到第 10 秒之间，原父进程已结束，子进程还在睡眠，是一个通常显示为 `S` 的孤儿进程。

| 时间段 | 原父进程 | 子进程 | 观察重点 |
|---|---|---|---|
| 约 0～3 秒 | 活着，多数时间 S | 活着，多数时间 S | 子进程 PPID 指向原父进程 |
| 约 3～10 秒 | 已经退出 | 仍在 `sleep(10)`，通常 S | 子进程 PPID 改为收养者，但自己的 PID 没变 |
| 约 10 秒后 | 已退出 | 自己也结束 | 后续退出状态应由新父进程回收 |

**原图里父进程不见了、子进程的 PPID 变成 1，应怎样读？**这是那次环境中 PID 1 接管了它的结果。不能据此推断所有环境一定相同，也不能把 PPID 变更理解为“子进程重新创建了一遍”。它仍然是原来的那个子进程，正在接着原来的控制流往下走。

**把 PPID 变化直接打印出来。文件名：`orphan_demo.c`。**

```c
/* 让子进程在原父进程退出前后分别读取 PPID。 */
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>

int main(void)
{
    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return EXIT_FAILURE;
    }

    if (pid == 0) {
        printf("child before: PID=%ld, PPID=%ld\n",
               (long)getpid(), (long)getppid());
        fflush(stdout);
        sleep(10);
        printf("child after:  PID=%ld, PPID=%ld\n",
               (long)getpid(), (long)getppid());
        return EXIT_SUCCESS;
    }

    printf("parent: PID=%ld; exit in 3 seconds\n", (long)getpid());
    fflush(stdout);
    sleep(3);
    exit(EXIT_SUCCESS);
}
```

新增的关键是子进程在 `sleep(10)` 前后各调用一次 `getppid()`：第一次通常读到原父进程；第二次在原父进程退出后读到收养者。这里不是“修改一个旧变量假装父进程变了”，而是再次向系统查询当前父关系。

一种可能的普通环境输出：

```text
parent: PID=5000; exit in 3 seconds
child before: PID=5001, PPID=5000
child after:  PID=5001, PPID=1
```

在有 subreaper 的环境中，最后的 PPID 可以是另一个非 1 数字。本笔记实际测试就观察到了子进程被测试用收养者接管，而不是 PPID 变为 1；这与手册规则一致。前几行的输出顺序仍不应写死。

**为什么终端已经出现命令提示符，后面又冒出子进程的一行输出？**因为在这个简单启动方式下，Shell 等到它直接启动的父进程结束，就可能重新提示你输入命令；子进程仍活着，并继承了连接该终端的输出描述符，稍后仍可能写到同一个终端。提示符重新出现，不等于所有后代进程同时消失。

实验中用睡眠只是让常见的先后关系容易观察；极端调度延迟下，“第一次打印一定发生在父退出之前”也不应当被当成同步保证。真正要求精确先后的程序需要显式同步。

**孤儿是不是不占资源、一定更安全？**不是。它仍是一个普通活进程，可能继续消耗大量 CPU、内存，或持有文件等资源。“孤儿”只描述父关系变化，不评价业务是否正常。收养者通常是在它结束后回收，不是接管后马上杀掉它；若收养者自身没有正确回收，也仍可能留下僵尸。[依据：subreaper 行为说明][subreaper]、[wait(2)][wait]

**父进程退出会不会必然让子进程退出？**普通本章实验没有这种默认连带关系。但服务管理器、终端信号、程序主动设置父进程死亡通知等机制可能改变结果，所以不能把实验结论扩大成“任何程序在任何环境下，父死子都绝不会受到影响”。[依据：exit(3) 对退出时信号行为的说明][exit]

### 1.4.5 父进程还要干别的：WNOHANG、多个子进程与实验排错

前面的阻塞 `waitpid()` 有一个特征：子进程没结束时，调用者停在等待接口中。若父进程还要处理其他事情，可以先询问“现在完成了吗”，没有完成就做其他工作，稍后再查。

这正是 `WNOHANG` 的用途。名字可以辅助记忆为“不在这次调用中挂住等结果”，但它**并不会让子进程加速完成，也不是后台执行符号**。对子进程未退出的情况，它让 `waitpid()` 返回 0；对子进程已经退出的情况，它同样能立即回收并返回该子进程 PID。[依据：wait(2)][wait]

**完整实验。文件名：`wait_nonblock.c`。**

```c
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return EXIT_FAILURE;
    }

    if (pid == 0) {
        sleep(5);
        exit(7);
    }

    while (1) {
        int status = 0;
        pid_t result = waitpid(pid, &status, WNOHANG);

        if (result > 0) {
            if (WIFEXITED(status)) {
                printf("reaped child PID=%ld, exit code=%d\n",
                       (long)result, WEXITSTATUS(status));
            } else if (WIFSIGNALED(status)) {
                printf("child killed by signal=%d\n", WTERMSIG(status));
            }
            break;
        }
        if (result == 0) {
            printf("child is not finished; parent can do other work\n");
            fflush(stdout);
            sleep(1);
            continue;
        }
        if (errno == EINTR) {
            continue;
        }
        perror("waitpid");
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```

先看这一轮循环会发生什么：

```text
调用 waitpid(..., WNOHANG)
├─ 返回正 PID：拿到退出状态 → 解码输出 → break，结束轮询
├─ 返回 0：还没结束 → 模拟父进程做其他事情 → sleep(1) → 下次再查
└─ 返回 -1：若是可重试的 EINTR 就重试，否则报告错误并结束
```

`break` 跳出当前循环，接着执行循环后面的代码；`continue` 跳过本轮后续语句，开始下一轮；`return` 则离开当前函数，在本例 `main()` 中意味着父进程结束。三者不是同一个“退出”。

```bash
gcc -std=c11 -Wall -Wextra -O0 wait_nonblock.c -o wait_nonblock
./wait_nonblock
```

你通常会先看到若干次“子进程还没结束，父进程可做别的工作”，随后看到退出码 7。重复提示次数不保证恰好为 5，因为启动、调度和轮询时机都有开销。

为什么要 `sleep(1)`？如果没有任何其他有用工作，只是在 `while (1)` 中极快地反复查询，就变成忙轮询，会无意义地消耗 CPU。示例用一秒等待降低轮询频率；真实事件驱动程序可以通过适当的通知机制处理，而不是照搬这一秒间隔。

**非阻塞轮询能保证从来不出现 Z 吗？**不能。如果子进程刚退出，父进程要过一会儿才进行下一次查询，那么中间可能短暂存在 Z；这里重要的是会被及时回收，而不是要求任何采样下都绝对看不到 Z。

**有多个子进程，调用一次 `wait()` 就全收了吗？**不是。一次成功等待通常只领取一个符合条件的子进程的状态。若创建了多个子进程，需要按设计逐个回收，或循环使用 `waitpid(-1, ..., WNOHANG)` 回收当前已经结束的子进程。用信号通知时，也不能假设一个 `SIGCHLD` 必然对应恰好一个待回收子进程，因为普通信号可能合并。[依据：wait(2)][wait]、[signal(7) 的普通信号排队规则][signal]

**有没有不调用 wait 也不留下僵尸的配置？**Linux 中，显式把 `SIGCHLD` 设置为 `SIG_IGN`，或配置 `SA_NOCLDWAIT`，可以改变子进程退出后的回收行为；但你也就不能按普通方式继续期待领取这些子进程的退出状态。要特别区分“默认动作被文档描述为忽略”和“程序显式设置 `SIG_IGN`”，两者在子进程回收语义上不是可以随便等同的。初学与需要退出结果的程序，优先把 `wait/waitpid` 学清楚，不要用忽略信号掩盖不懂回收逻辑的问题。[依据：wait(2) Linux 说明][wait]

**把两个概念最后对照一次：**

| 比较项 | 僵尸进程 | 通常所说的孤儿进程 |
|---|---|---|
| 关键事实 | 子进程已结束，退出记录尚未回收 | 原父进程先退出，子进程仍存活 |
| 能否继续执行自己的业务代码 | 不能 | 可以，具体还要看它当前的 R/S/T 等状态 |
| 是否有专门的 `ps` 状态字母 | 有，Z | 没有，“孤儿”不是新字母 |
| 核心观察 | Z、PPID、是否长期未回收 | 原 PPID 改变、自身 PID 仍相同 |
| 资源 | 保留必要内核管理信息，不是整个工作内存都还在 | 仍可能占正常运行所需的各种资源 |
| 正确处理方向 | 由父进程或收养者回收，修复长期遗漏回收的代码 | 按业务决定是否继续，由合适收养者管理后续退出 |

“父死子活、子死未收”可以帮助记忆，但不能代替上面关于实际状态、收养者和资源的解释。

**实验不符合预期时，按现象定位：**

| 现象 | 优先检查 |
|---|---|
| `gcc: command not found` | 当前 Linux 环境没有找到编译器，不是 `fork()` 语法有问题 |
| 报 `fork` / `sleep` 没声明 | 是否漏了正确头文件，是否把截图代码缺行照抄进来 |
| `./zombie_demo: No such file or directory` | 编译是否成功、当前目录是否正确、输出文件名是否一致 |
| 只看到父或只看到子 | 是否运行太久才观察；筛选了错误名称；示例本来已经进入不同生命周期阶段 |
| 重复运行得到不同 PID、不同输出顺序 | 一般正常，PID 分配与调度先后不是固定答案 |
| 重定向以后输出似乎延迟 | 检查标准 I/O 缓冲，示例关键位置已加 `fflush(stdout)` |
| 孤儿的新 PPID 不是 1 | 检查是否有 subreaper、容器等环境，不要因此直接判错 |
| 普通程序一直是 S | 看是否在正常等事件；“程序已启动”不等于必须一直 R |
| 非阻塞 `waitpid` 返回 0 | 这次还没拿到退出状态，不是拿到退出码 0 |
| `waitpid` 报 `ECHILD` | 没有符合条件的未回收子进程，可能已经收过、不是自己的子进程，或配置了自动回收 |

**本笔记的实际验证范围：**附带的 8 个完整 C 程序均使用 `gcc -std=c11 -Wall -Wextra -Werror -O0` 编译通过；测试环境实际观察到了忙循环 `R → T → R`、睡眠 S、子进程 Z、非 1 的收养者 PPID、退出码 7，以及等待后子进程记录消失。测试在独立 Linux 容器中进行，不是在你的服务器上；没有人为制造 D、调试器 t，也没有把 SSH 断开或交互式作业控制宣称为已经实测。代码包附有验证记录。

## 1.5 把进程状态用于实际操作：信号、前后台与优先级

### 1.5.1 `kill` 到底做什么，怎样安全地暂停、继续和结束实验

**`kill` 的本质是发送信号，不是名字里有“kill”就一定杀死。**可以发送“请结束”，也可以发送“暂停”或“继续”。发送成功表示内核接受了相应请求，不表示目标已经处理完成，更不表示它的父进程已经回收了退出记录。[依据：kill(2)][kill2]

| 信号 | Linux 中常见编号 | 常见作用 | 对初学者最重要的区别 |
|---|---:|---|---|
| `SIGTERM` | 15 | 请求终止，程序可以设置处理逻辑 | 通常作为正常结束请求；不保证任意程序都一定有完善的收尾逻辑 |
| `SIGKILL` | 9 | 强制终止，不能捕获、忽略或阻塞 | 程序无法运行自定义信号处理函数进行收尾；不是修复 Z 或底层 I/O 故障的方法 |
| `SIGSTOP` | 19（常见架构） | 停止执行 | 不能捕获或忽略，进程没有因此完成退出 |
| `SIGCONT` | 18（常见架构） | 解除作业控制停止 | 恢复后仍要遵守调度和原有等待条件 |
| `SIGINT` | 2 | 终端中常见的中断请求 | `Ctrl+C` 通常发送它，默认动作是终止 |
| `SIGTSTP` | 20（常见架构） | 终端中常见的暂停请求 | `Ctrl+Z` 通常发送它，可以被捕获或忽略 |

信号编号存在架构差异，所以实践优先使用 `TERM/STOP/CONT` 等名字，不要把所有编号当成跨系统固定规则。这里表格帮助你看懂资料中的 `15` 和 `9`，不是要求背完整信号表。[依据：signal(7) 的信号与架构说明][signal]

**一个可控的 `R → T → R` 实验。**先在终端 A 运行前面的 `./busy_demo`；终端 B 找到它的 PID。下面的 `12345` 只是占位数，必须换成你刚刚确认的实验 PID，不要照着示例数字结束别人的进程。

```bash
# 终端 B：先确认名称与 PID
pgrep -ax busy_demo

# 把以下 12345 换成自己的 busy_demo 的 PID，再逐行执行
ps -p 12345 -o pid,ppid,stat,comm
kill -STOP 12345
ps -p 12345 -o pid,ppid,stat,comm
kill -CONT 12345
ps -p 12345 -o pid,ppid,stat,comm
kill -TERM 12345
```

第一次通常能看到 `R`；STOP 生效后可看到 `T`；CONT 解除停止后忙循环重新具备运行资格，通常又是 `R`。最后 TERM 让这个没有自定义处理逻辑的示例结束。状态改变是异步发生的，观察命令若执行得极快，可能需要稍后再取一次快照。

**为什么先 TERM，不直接 KILL？**程序收到 TERM 时，有机会按自己的设计停止接收新任务、保存必要状态、关闭业务连接；KILL 不提供这种用户态收尾机会，可能造成业务数据丢失或留下不完整结果。因此一般先尝试正常停止，并结合业务允许的时间观察；确认必要后才考虑 KILL，而不是机械地给所有进程发送 `-9`。[依据：signal(7)][signal]、[exit(3)][exit]

```bash
kill 12345         # 通常等价于 kill -TERM 12345
kill -KILL 12345   # 仅在确认需要强制结束自己的实验进程时使用
```

权限也有影响：普通用户通常只能向符合权限规则的进程发送信号；系统可能报告 `Operation not permitted`。`No such process` 则可能是目标已经退出或 PID 写错。不要看到失败就立刻加 `sudo`，应先确认目标和原因。[依据：kill(2) 的权限与错误][kill2]

**`killall` 与 `kill PID` 的区别。**在本章讨论的 Linux `killall` 中，`killall -TERM busy_demo` 会按进程名匹配并向所有符合条件的实例发信号；`kill -TERM 12345` 则指定一个 PID。前者方便，却更容易一次影响多个实例。真实服务环境优先确认具体 PID，不要随手执行针对 `bash`、`python`、`test` 等通用名字的批量终止命令。[依据：killall(1)][killall]

对于僵尸，停止/继续/再次杀死都不能让它重新运行或替代回收；对长期 D，也要定位等待的资源。**先读状态，再决定操作，不能把所有“不符合预期”都归结为“杀不干净”。**

### 1.5.2 前台、后台、`jobs/fg/bg` 与 `nohup`，逐个符号解释

“前台/后台”和“R/S/T/Z”不是同一种分类。前后台讨论的是进程所在的作业与当前终端之间的关系；状态讨论的是它当前能否运行、是否等待、是否已经退出。**后台进程也会是 R，前台进程也会是 S。**例如前台的 `sleep 30` 通常在等时间，后台的忙循环仍可能持续使用 CPU。[依据：Bash 作业控制][bash]、[ps(1)][ps]

为了练习，保存下面脚本为 `long_run.sh`。脚本是 Shell 命令组成的文本，不需要 GCC 编译。

```bash
#!/usr/bin/env bash
# 仅作前后台与 nohup 练习，每隔 5 秒写一行；实验后停止对应作业。
while true; do
    printf 'script PID=%s is alive\n' "$$"
    sleep 5
done
```

第一行说明脚本希望使用 Bash；因为下面明确用 `bash long_run.sh` 运行，即使没有给脚本添加可执行权限，也可以由 Bash 读取执行。`while true` 是持续循环；`printf` 每次打印一行，`%s` 用于放入文本；`$$` 在这个脚本中表示该 Bash 实例的 PID；`sleep 5` 让循环不要持续空转。[依据：Bash 特殊参数与执行命令][bash]

**先体验前台。**运行 `bash long_run.sh` 后，你的这个终端正在把前台交给脚本；没有出现新的 Shell 提示符时，不要把输入普通文字误认为在执行新的 Shell 命令。可以按 `Ctrl+C` 结束这项前台练习。需要持续观察时，用另一个终端运行 `ps`，不要靠猜程序还在不在。

**再体验后台。**

```bash
bash long_run.sh &
```

末尾 `&` 让 Shell 把这项工作放到后台启动，Shell 不必等它结束就能继续接收命令。你可能看到：

```text
[1] 4200
```

`[1]` 是**当前 Shell 的作业编号**；`4200` 是这次后台任务对应的进程编号信息。它们不是同一种编号，数字也不必一致。对于包含管道的复杂作业，一个作业可以包含多个进程，更不能把“一个作业永远只有一个 PID”当成规则。[依据：Bash 作业控制与异步命令][bash]

后台不等于输出自动消失。没有重定向时，脚本的输出仍可能混在你的命令提示符附近。可以通过下面的命令查看和管理：

```bash
jobs -l          # 查看当前 Shell 的作业，-l 同时显示相关 PID
fg %1            # 把作业 1 调回前台；若它已暂停，通常同时继续它
# 此时在前台按 Ctrl+Z：暂停该作业，Shell 重新给出提示符
bg %1            # 让已暂停的作业 1 在后台继续运行
jobs -l
```

这里 `#` 开头的是注释，不是需要输入的程序输出；`%1` 是 Bash 的作业引用语法，不是系统 PID 1。**`bg` 的作用是“在后台继续”，不是“把进程暂停”。**暂停动作来自 `Ctrl+Z` 或相应停止信号；`fg/bg` 负责继续及前后台安排。[依据：Bash 的 `jobs`、`fg`、`bg`][bash]

`jobs` 中的 `Running` 表示“这项作业没有处于 Shell 所记录的暂停或完成状态”，不能据此断定 `ps` 的状态必然是 R。我们的后台脚本大部分时间都在等待 `sleep`，出现 S 很正常。你在另一个新终端执行 `jobs`，也不一定能看到原终端的任务，因为两个 Shell 有各自的作业表。

**练完怎样结束？**确认 `jobs -l` 中仍是自己的脚本后，可以 `fg %1` 调回前台，再按 `Ctrl+C`；也可以在启动它的同一个 Bash 中用 `kill -TERM %1` 向该作业发送结束请求。作业号请以当前输出为准，不要始终认定为 1。脚本会创建短暂的 `sleep` 子进程；按作业/前台进程组处理，比只凭一个旧 PID 猜测整个作业是否结束更合适。

**`&` 能保证退出 SSH 后程序继续吗？**不能。`&` 只处理“是否在 Shell 后台”，不等于摆脱终端、挂断信号和会话清理策略；但是反过来说“所有 `&` 程序一关闭终端必定死亡”也过于绝对。实际结果与 Shell 配置、终端行为、信号处理、会话管理有关。[依据：Bash 的退出信号与作业控制][bash]

**`nohup` 用于忽略挂断信号，但它本身不会自动把命令放后台。**常见写法如下，保留末尾的 `&`：

```bash
nohup bash long_run.sh > my_log.log 2>&1 < /dev/null &
```

不要一口气背整行，拆开看：

| 片段 | 作用 | 执行后的实际含义 |
|---|---|---|
| `nohup` | 让所启动命令忽略挂断信号 SIGHUP | 降低因挂断信号而退出的风险，不是“永不结束” |
| `bash long_run.sh` | 用 Bash 执行指定脚本 | 脚本里的命令开始逐步执行 |
| `> my_log.log` | 把标准输出重定向到文件 | 正常输出不再写向当前终端；同名文件通常会被截断重写 |
| `2>&1` | 让标准错误也指向此刻标准输出的去向 | 错误输出和正常输出一起进入 `my_log.log` |
| `< /dev/null` | 把标准输入接到空设备 | 不再等待从当前终端读取交互输入 |
| 末尾 `&` | 后台启动整条命令 | 当前 Shell 可以继续接收下一条命令 |

这里涉及三个常见文件描述符：**0 是标准输入、1 是标准输出、2 是标准错误**。描述符可以先理解成进程使用的一组“打开的输入/输出通道编号”；它们不是全系统只有三个，也不是编号 1 永远只能通往终端。`>` 没写编号时默认操作标准输出 1，`<` 默认操作标准输入 0。[依据：Bash 重定向][bash]

`2>&1` 中间的 `&` 表示后面的 `1` 是描述符编号，不是文件名；行末的 `&` 表示后台启动。虽然写的是同一个字符，但语法位置不同、作用不同；更不要与 C 中的 `&status` 取地址或 `&&` 逻辑与混为一谈。

**为什么顺序重要？**Shell 按从左到右建立重定向。第一种先把 1 接到文件，再让 2 复制 1 的当前去向；第二种先把 2 接到当时仍然指向终端的 1，然后只改变 1，所以错误输出可能仍留在终端。

```bash
command > my_log.log 2>&1     # 标准输出、标准错误都进文件
command 2>&1 > my_log.log     # 顺序不同，标准错误不因此跟着后改的 1 自动搬走
```

这里 `command` 是说明语法用的占位名称，应换成实际命令，不是让你原样运行。需要在原日志末尾追加时用 `>> my_log.log`，不是 `>`。显式写了 `> my_log.log` 后，输出目标就是你指定的日志，不能像截图注释那样又统一说“输出到 `nohup.out`”；`nohup.out` 是某些未显式重定向情形下的默认处理。[依据：nohup(1)][nohup]、[Bash 重定向][bash]

可以用 `jobs -l`、`ps` 和查看日志的方式确认程序是否仍在执行。`nohup` 不会抵抗 `SIGKILL`、程序自身错误、重启、资源限制或额外的会话清理策略，也不会自动把程序变成配置齐全的系统服务。必须依赖终端输入的交互程序，也不能简单加一层 `nohup` 就当作可靠后台服务。

### 1.5.3 `nice/renice`：调整竞争 CPU 的倾向，不是修改进程状态

当多个可运行任务竞争 CPU 时，调度策略及相关参数会影响谁获得多少执行机会。**nice 值越小，通常越有利于普通调度任务竞争 CPU；越大，越“谦让”。**Linux 常见取值为 `-20～19`，普通交互环境的初始值常见为 0，但进程可以继承其他 nice 值，不能认为每个新进程必定从 0 开始。[依据：nice(1)][nice]、[sched(7)][sched]

| 数值示意 | 直观理解 | 不代表什么 |
|---|---|---|
| `-5` | 相对于 0 更积极地争取 CPU | 不代表独占 CPU，也不自动变成实时任务 |
| `0` | 常见基准值 | 不表示没有调度规则 |
| `10` | 相对于 0 更谦让 | 不代表最多只能用 10% CPU |
| `19` | 普通 nice 范围里更谦让的一端 | 不表示永远不会运行 |

**`nice` 用于启动新命令，`renice` 用于调整已有任务。**

```bash
nice -n 10 ./busy_demo
```

这里 `-n 10` 是相对当前继承 nice 值增加 10，并非无条件设为绝对 10。若当前为 0，启动后的示例常见为 10；若继承值本来不为 0，结果就不能照这个数字猜。实验是忙循环，观察完仍要按 `Ctrl+C` 结束。[依据：nice(1)][nice]

截图的 `nice -n -5 ./app` 表示相对继承值降低 5，也就是提高竞争优先级；这里 `./app` 是教程假设存在的可执行文件，不是 Linux 自带命令。提高这种优先级通常需要相应权限或资源限制允许，并不严谨地等于“只有 root 永远可以、非 root 永远不行”。实际可能涉及 `CAP_SYS_NICE` 和 `RLIMIT_NICE`。[依据：sched(7)][sched]、[renice(1)][renice]

已有进程可以这样调整，PID 同样必须换成你确认的实验进程：

```bash
ps -p 12345 -o pid,ni,pri,stat,comm
renice 10 -p 12345
ps -p 12345 -o pid,ni,pri,stat,comm
```

在这里使用的 Linux `renice` 常规语义下，`10` 表示把 nice 值设到 10，而不是再增加 10。其不同选项及 `POSIXLY_CORRECT` 环境变量可能影响特定写法，长期脚本应核对本机手册，不能机械地把 `nice` 和 `renice` 的所有参数语义视为相同。`NI` 是 nice 值，`PRI` 是工具显示的调度优先级字段，它们不是“CPU 百分比”。[依据：renice(1)][renice]、[ps(1)][ps]

为什么改完 nice，CPU 使用率可能还是很高？因为如果 CPU 没有别的有竞争力的可运行工作，就没有必要让它空闲。nice 主要影响竞争时的安排，不是固定配额；实际还受调度策略、控制组等因素影响。睡眠等待的进程也不会因为 nice 更小就自动得到输入，僵尸更不会因为提优先级而复活。**状态决定“现在是否有资格执行”，优先级帮助决定“有资格的任务怎样竞争”，两者要分开。**[依据：sched(7)][sched]

## 1.6 纠正常见误区，并练习有来源的面试与笔试题

### 1.6.1 对照原资料，哪些结论不能直接照抄

这一节不是让你再背一份定义，而是防止把教程的简写当成严格结论。相关原理、证据和实验已在前面给出。

| 容易记错的说法 | 应改为 |
|---|---|
| `R` 就是此刻正在占用 CPU | R 包括正在运行和可运行、等待 CPU；要和教材“运行”小框区分 |
| 七状态图每个框都能找到一个对应的 `ps` 字母 | 通用教材模型与 Linux 用户可见状态不是一一映射 |
| “挂起”就是内存全部换出，等于 Linux T | 教材挂起、分页换出、Shell 暂停是不同层面的概念 |
| 等 I/O 都是 D；D 只能是磁盘 | 等待实现不同，S 和 D 都可能涉及 I/O；D 不只限于物理磁盘 |
| SIGKILL 不可忽略，所以任何目标都会瞬间消失 | 信号发送、实际终止和退出记录回收是不同步骤；D、Z 尤其不能这样推断 |
| 子进程调用 `exit()` 后马上什么都没有 | 业务执行结束，但通常还保留待回收的退出信息 |
| 父进程 `sleep()` 就是在回收子进程 | sleep 只是等时间，不调用 wait 系列就不会因此领取退出状态 |
| 父睡 30 秒、子睡 5 秒，会产生 30 秒僵尸 | 从子退出到父后续回收/退出的观察窗口约为 25 秒，受调度影响 |
| 僵尸把子进程全部内存一直保留着 | 保留必要内核记录；不是工作中的所有堆、栈都原封不动留着 |
| 孤儿一定被宿主系统 PID 1/systemd 收养 | 可能由最近的祖先 subreaper 或相应 PID 命名空间的 init 收养 |
| 孤儿不会占用多少资源 | 孤儿仍可正常运行，资源占用由它实际做的工作决定 |
| `waitpid` 返回 0 说明子进程成功退出 | 使用 WNOHANG 时，0 说明本次还没有可领取的所需状态 |
| `waitpid` 返回值就是 `exit(7)` 中的 7 | 成功返回子进程 PID；退出码要从写入的 status 中按宏解码 |
| `ps aux \| grep Z` 就能可靠找出所有僵尸 | 它只是搜整行字符 Z，可能误匹配命令名等；应根据状态字段筛选 |
| `bg` 把前台进程暂停到后台 | 先通过暂停信号停下，再由 bg 在后台继续 |
| `&`、`nohup` 都能保证程序永远运行 | & 管前后台，nohup 主要管 SIGHUP；两者都不是永不失败或重启自恢复机制 |
| nice 值就是 CPU 使用比例 | 它影响普通任务竞争 CPU 的倾向，不是百分比限额 |

### 1.6.2 面试题与代码推演：6 道可追溯问法，4 道原创训练

**来源先说明白：**下面“真实面经题”来自候选人在牛客公开发布的第一人称面试记录，证明的是“该作者报告曾被问到这一主题”，不是企业官方题库，也不能独立核验面试现场。题目按原记录主题转述，答案由本笔记依据官方技术资料重新组织；没有把面经作者的回答照搬成标准答案。后 4 题是原创练习，明确不冒充任何公司的真实笔试原题。

**题 1【真实面经主题｜字节跳动后端，2019】进程有哪些状态，状态之间如何转换？**

出处：[《字节跳动 一二三面面经 刚改头像就收到offer call》][interview-byte-2019] 中记录了进程状态及转换追问。

**回答主线：**先说教材的就绪、运行、阻塞，解释“缺 CPU”和“缺事件”的区别；再说明 Linux 的 R 合并运行与可运行，常见 S 是可中断等待、D 是不可中断等待，T/t 分别与作业控制停止和调试暂停有关，Z 是执行结束但尚未回收的退出记录。不能把这两套层级直接混为一谈。

转换可以口头举例：一个任务计算时是 R，调用需要等待的接口后可能进入 S；条件满足后被唤醒，恢复可运行 R；获得 CPU 后继续执行。若被抢占但没有阻塞，仍可能是 R。退出后按普通回收规则留下 Z，父进程领取状态后不再可见。面试官问七状态时，再补充“是否挂起”这个维度，不要把所有知识一股脑背出来。[技术核对：ps(1)][ps]、[wait(2)][wait]

**题 2【真实面经主题｜字节跳动后端，2019】等待状态能收到信号吗？S 和 D 有何区别？**

出处：同一篇 [字节跳动面经][interview-byte-2019] 明确记录了等待态是否能收到信号，并关联 S/D 的追问。

**参考回答：**需要区分“信号被发送或成为待处理状态”与“当前等待是否立即被打断”。S 允许适当的信号打断等待，后续可能执行信号处理、返回 EINTR 或按规则重启某些调用；D 对普通信号不可中断，某些终止请求要等离开等待路径才能完成。不能答“D 根本不可能被发送信号”，也不能答“有 SIGKILL 就必然瞬间消失”。若进一步追问内核细节，再补充 TASK_KILLABLE 等组合状态，不要把所有显示 D 的情况绝对化。[技术核对：signal(7)][signal]、[内核任务标志][kernel-sched]

**题 3【真实面经主题｜腾讯 WXG C++ 后台，2018；字节跳动后端，2019】`fork()` 后发生了什么，为什么父子进程能走不同分支？**

出处：[腾讯 WXG 实习面经][interview-tencent-2018] 记载了 fork 的深入追问；[字节跳动面经][interview-byte-2019] 也记载 fork 后内存及写时复制问题。腾讯帖子后续编辑时间不同，本文按正文写明的 2018 年面试时间标注。

**参考回答：**fork 成功后形成父、子两个执行流，两者都从调用返回位置往下走；父进程得到子 PID，子进程得到 0，所以能用返回值选择各自分支。父子是不同进程，PID 不同，普通私有变量不会因为名字相同就自动同步。Linux 通常通过写时复制避免立刻复制全部物理页；某一方修改相关私有内存页时，才按需复制，不能说成“只复制一个被修改的 C 变量”。父子谁先得到 CPU 没有通用固定保证。[技术核对：fork(2)][fork]

可加一个短例子：fork 前 `a=10`，子进程把私有变量 `a` 改成 20，父进程自己的 `a` 不因此自动变 20。共享内存、共享文件等是另一个问题，不能用这个例子否认所有形式的数据共享。

**题 4【真实面经主题｜腾讯 WXG C++ 后台，2018】什么是僵尸进程？为什么需要保留它，会有什么影响？**

出处：[腾讯 WXG 实习面经][interview-tencent-2018] 记录了僵尸定义的追问；这里把“为什么保留及其影响”作为解释该定义的延伸，不声称后两句是面试官原话。

**参考回答：**子进程已经执行结束，但父进程尚未领取退出状态时，通常保留一份必要记录，呈现 Z。保留的目的是让父进程知道是否正常退出、退出码等，不是继续执行代码。单个短暂 Z 可以是正常交接过程；大量长期积累会占用内核管理记录和进程标识相关资源，影响继续创建进程。它不是“整个程序仍占满原先内存”，也不是应该再对它执行一次 kill 的活进程。[技术核对：exit(3)][exit]、[wait(2)][wait]

**题 5【真实面经主题｜腾讯 WXG C++ 后台，2018】怎样避免子进程退出后长期变成僵尸？**

出处：[腾讯 WXG 实习面经][interview-tencent-2018] 记录了避免僵尸进程的追问。

**参考回答：**由父进程正确等待和回收，例如只需等一个子进程时使用 waitpid；父进程还要处理其他工作时，可以使用适当的非阻塞或通知机制。多个子进程应逐个领取所有已经结束的状态，不能认为一次 wait 或一次信号通知就自动处理了全部子进程。对不需要退出结果的特定设计，可讨论显式 SIGCHLD 忽略或 SA_NOCLDWAIT，但这改变结果领取语义，不宜盲目套用。线上发现 Z 时应查 PPID 和父进程的回收逻辑，而不是把“杀父进程”当作无风险常规修复。[技术核对：wait(2)][wait]、[signal(7)][signal]

**题 6【真实面经主题｜腾讯 WXG，2024】僵尸进程与孤儿进程有什么区别？**

出处：[《腾讯WXG前端面经》][interview-tencent-2024] 明确列出“僵尸进程与孤儿进程”。岗位是前端，不应擅自改写成该公司的 C++ 笔试。

**参考回答：**僵尸关注“子进程已结束，但退出信息未回收”；通常所说的孤儿关注“原父进程先退出，子进程仍存活”。僵尸不能继续执行业务代码，孤儿可以继续运行，而且可能是 R/S/T 等不同状态。孤儿的原 PPID 会变为收养者，收养者不一定是宿主 PID 1；它最终退出后的结果也需要被正确回收。两者不是“一个坏进程、一个不占资源的好进程”这么简单。[技术核对：wait(2)][wait]、[PR_SET_CHILD_SUBREAPER][subreaper]

**题 7【原创笔试训练】按时间线判断状态，而不是只看函数名字。**

下面是只保留关键逻辑的题目片段，不是可单独编译的完整程序。假设 fork 成功、没有额外信号、系统正常调度，睡眠时长只取近似值。

```c
pid_t pid = fork();
if (pid == 0) {
    sleep(5);
    exit(7);
}
sleep(12);
int status = 0;
pid_t result = waitpid(pid, &status, 0);
printf("%ld %d\n", (long)result, WEXITSTATUS(status));
```

问：①第 2 秒父子通常是什么状态？②第 8 秒呢？③僵尸窗口大约多长？④打印的两个数字分别是什么？⑤将父进程 `sleep(12)` 改成直接 waitpid，发生什么变化？

**解析：**子进程进入 if 后先睡 5 秒，再 exit，所以不会掉下来执行父进程那段 `sleep(12)`。第 2 秒父子通常都在 S；第 8 秒子已退出为 Z，父仍睡眠为 S；约第 12 秒父醒来回收，僵尸窗口约 7 秒。成功回收后，前一个数字是子 PID，后一个是退出码 7，不是“两个都是 7”。若父一开始就 waitpid，它会等待子进程完成，而不是固定等 12 秒，子退出后即可被及时回收。

题目为突出流程，省略了 fork/waitpid 失败处理和 WIFEXITED 检查；真实代码必须像 `wait_demo.c` 那样先判断返回值与退出方式，不能直接照这段精简片段编写生产代码。父子启动的细小时差意味着“第 2 秒、第 8 秒”是教学近似，不是硬实时保证。

**题 8【原创代码训练】两次 `fork()` 为什么不是总共 3 个进程？**

```c
/* 逻辑片段：假设两次调用在所有相关进程中均成功。 */
fork();
fork();
printf("X\n");
```

**答案：包含最初进程，总共 4 个执行流，`printf` 会由它们各执行一次。**第一次 fork 后有 A、B；第二行不是只由 A 执行，而是 A、B 都会执行，所以 A 产生 C，B 产生 D。总共 A/B/C/D，不是简单把“代码里出现两次 fork”算成“只增加两个”。

```text
第一次后：A、B
第二次后：A→新增 C，B→新增 D
最终执行 printf：A、B、C、D，共 4 次
```

不要因此推广为“屏幕上出现几行就是几个进程”。若在 fork 前有尚未刷出的标准 I/O 缓冲内容，它也可能随地址空间复制，并在不同进程退出时各自被刷出，导致观察混淆；这里的 X 是两次 fork 后才调用 printf，讨论的是这段明确位置的执行次数。短题省略了完整回收逻辑，实际多子进程程序仍须正确 wait。[技术核对：fork(2)][fork]、[exit(3)][exit]、[fflush(3)][fflush]

**题 9【原创场景题】服务器上出现大量长期 Z，你先检查什么，为什么不直接批量 `kill -9`？**

**参考步骤：**先用带明确列名的 `ps -eo pid,ppid,stat,comm` 查看状态字段，确认确实为 Z，而不是命令行文字恰好有 Z；再观察它们是否集中于相同 PPID。核对该父进程的职责、是否长期未执行回收、是否有错误分支绕过 wait、是否只处理了部分子进程。必要时结合日志和受控调试定位；针对线上父进程的重启、停止必须评估业务影响并按既有运维流程进行。[工具依据：ps(1)][ps]

不能通过 SIGKILL 让已经结束执行的僵尸“再死一次”。直接批量杀父进程还可能中断正常业务；即使收养者随后处理了退出记录，也不等于原软件中的回收缺陷已经修好。答题应体现“确认状态 → 找父进程 → 查回收路径 → 受控修复”，而不是只背一行危险命令。[原理依据：wait(2)][wait]

**题 10【原创找错题】`waitpid` 返回 0，下面的代码为何会误报成功？**

```c
/* 错误示范片段：不要作为正确等待逻辑使用。 */
int status = 0;
pid_t result = waitpid(pid, &status, WNOHANG);
if (result >= 0) {
    printf("child exit code = %d\n", WEXITSTATUS(status));
}
```

**答案：错在把“没有错误返回”当作“已经拿到子进程状态”。**WNOHANG 下 result 为 0 时，子进程可能还没结束，本次没有取得退出状态；status 的初始化值 0 只是父进程自己写进去的，不是子进程汇报的成功。正确逻辑是 result > 0 才分析这次取得的状态，并先检查 WIFEXITED；result == 0 继续做其他工作、以后再查；result == -1 处理错误与必要重试。完整正确写法见 `wait_nonblock.c`。[技术核对：wait(2)][wait]

**口头回答的小技巧：**先给定义，再说为什么，最后用本章某个实验说明。例如“Z 是退出未回收；保留它是为了交接退出结果；在父睡 30 秒、子睡 5 秒的实验中，大约第 5～30 秒能看到它”。这样比只说“子死父没收”更能体现理解；如果没有亲自运行过实验，应诚实说“示例中”，不要说成自己处理过真实线上事故。

## 1.7 一眼复习：把整章压回一张知识地图

**一句话主线：**进程不是一直占 CPU；活着时可能执行、等 CPU、等事件或被暂停；执行结束后，还可能要把退出结果交给父进程。

| 状态 | 最短准确理解 | 典型判断 |
|---|---|---|
| R | 正在运行，或已就绪等 CPU | 时间片结束后仍可能是 R |
| S | 可中断等待 | sleep、等输入、等子进程；多次 S 不代表从未运行 |
| D | 不可中断等待 | 常见某些内核 I/O 等待；kill 不保证立即结束 |
| T / t | 作业控制停止 / 调试暂停 | 还活着，不是已经退出 |
| Z | 已结束，退出记录未回收 | 不再执行业务代码；查父进程回收逻辑 |
| X / I | 内部死亡标记 / 空闲内核线程 | 普通应用入门不必刻意制造 |

```text
教材：就绪 → 得到 CPU → 运行 → 等事件 → 阻塞 → 事件满足 → 就绪
Linux：就绪和正在执行都可为 R；R → 等待 S/D → 被唤醒为 R
普通退出：结束业务执行 → Z（保留结果）→ 父进程 wait/waitpid → 完成回收
孤儿：原父先退出 → 子继续存在 → PPID 变为合适收养者；自己的 PID 不因此改变
```

| 必须分清的值/操作 | 记忆方式 |
|---|---|
| fork 返回值 | 父得子 PID，子得 0，失败 -1；父子从返回处继续 |
| waitpid 返回值 | 正数是被等待的子 PID；WNOHANG 的 0 是暂时没结果；-1 是错误 |
| 子进程退出码 | 从 status 解码：先 WIFEXITED，再 WEXITSTATUS，不把 PID 当退出码 |
| `sleep()` 与 `waitpid()` | 一个等时间，一个等待/领取子进程状态；sleep 不会自动回收 |
| `exit(7)` 与 main 的 return | 当前进程退出；普通函数 return 只返回调用者，不一定退出进程 |
| `SIGSTOP` / `SIGCONT` / `SIGTERM` | 暂停 / 继续 / 请求终止；SIGKILL 不提供用户态收尾机会 |
| `&` / `nohup` / nice | 后台启动 / 主要忽略 SIGHUP / 调整普通任务竞争倾向；三者都不是状态字母 |

**常用观察命令：**`ps aux` 看整体，`ps ajx` 看父子及作业关联，`ps -p PID -o pid,ppid,stat,comm` 精确看目标，`pgrep -ax 名称` 找实例，`pstree -p` 看进程树，`jobs -l` 看当前 Shell 的作业。

**用四个实验恢复理解：**忙循环易见 R；循环打印后 sleep 多见 S；父睡 30 秒、子睡 5 秒，通常约 25 秒可见子 Z；父睡 3 秒退出、子睡 10 秒，子自身 PID 不变但 PPID 改为收养者。

**最后自测：**没有 CPU 和没有输入为什么不同？exit 之后为什么还能 ps 到？waitpid 的 PID 与 status 为什么是两条信息通道？孤儿的新父亲为什么未必是 1？能用自己的话讲通这四问，再运行一次实验，这一章的骨架就建立起来了。
