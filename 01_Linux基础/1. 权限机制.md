# 01 Linux Shell：用户和内核之间的命令解释器

## 1.1 Linux 系统中「内核」和「Shell」分别是什么

Linux 严格意义上的核心是 **内核 kernel**。内核负责管理硬件和底层资源，例如 CPU 调度、内存分配、进程管理、文件系统、网络协议栈、设备驱动等。普通用户不能直接对内核说“帮我打开文件”“帮我创建目录”，因为内核只接受系统调用这种底层接口。

Shell 是用户和内核之间的 **命令解释器**。你在终端输入 `ls -l`，Shell 会读取这行命令，解析出命令名和参数，找到对应程序，然后让操作系统执行，最后把结果显示回终端。

可以把 Shell 理解为银行前台：用户不会直接进入银行金库操作现金，而是把需求告诉柜员；柜员检查你的身份和请求，再通过内部系统完成操作。Shell 就像这个“柜员”，内核就像银行内部系统。

## 1.2 Shell、终端、bash 的区别

| 名称 | 作用 | 举例 |
|---|---|---|
| 终端 Terminal | 提供输入和输出的窗口/设备 | GNOME Terminal、iTerm2、VS Code Terminal |
| Shell | 命令解释器，负责解释命令 | bash、zsh、sh、fish |
| bash | 最常见的一种 Shell | Linux 默认常见 Shell |
| 内核 kernel | 操作系统核心 | Linux kernel |

新手最容易混淆：你打开的是“终端窗口”，终端里面运行的是“Shell 程序”，常见 Shell 是 `bash` 或 `zsh`。

查看当前使用的 Shell：

```bash
echo $SHELL
```

查看当前 Shell 进程：

```bash
ps -p $$
```

其中 `$$` 表示当前 Shell 的进程 ID。

## 1.3 常见 Shell 类型

| Shell | 说明 |
|---|---|
| `sh` | 传统 Bourne Shell，很多脚本用 `#!/bin/sh` 保证兼容性 |
| `bash` | Bourne Again Shell，Linux 上最常见，功能强，适合学习和脚本编写 |
| `zsh` | macOS 新版本默认 Shell，交互体验更强 |
| `fish` | 更友好的交互式 Shell，但脚本语法和 bash 不完全兼容 |

面试中一般默认讨论的是 `bash`，但实际线上脚本建议写得尽量 POSIX 兼容，或者明确写 `#!/bin/bash`。

## 1.4 面试高频题：Shell 是什么？Shell 和内核是什么关系？

**题目：请解释 Shell 和 Linux 内核的关系。**

**参考回答：**  
Linux 内核负责真正管理系统资源，例如进程、内存、文件系统和设备；Shell 是用户态程序，是命令解释器。用户在终端输入命令后，Shell 负责读取、解析、查找并执行命令。执行外部命令时，Shell 通常会创建子进程，再通过系统调用让内核完成进程调度、文件访问等操作。因此 Shell 不是内核，而是用户和内核之间的交互层。

> 你在终端输入一个命令（比如 `ls`、`cat`、`mkdir`），**Shell 不会自己去执行这个命令**，而是：
>
> 1. 先**fork()** → 克隆出一个**子进程**
> 2. 让**子进程**去执行命令
> 3. Shell 自己在旁边等着，不阻塞
>
> **为什么要创建子进程？**
>
> - 不让 Shell 自己崩溃
> - 不让 Shell 被命令卡住
> - 可以同时运行多个命令
> - 方便管理、回收资源
>
> **简单比喻：**
>
> Shell 是老板，不亲自干活，**派员工（子进程）去干活**。

> **什么是系统调用？**
>
> 就是**用户程序 → 内核**的**唯一合法入口**。
>
> 用户程序（包括 Shell、子进程）**不能直接碰内存、CPU、硬盘**，必须通过系统调用请求内核。
>
> 流程是这样的：
>
> 1. 你输 `ls`
> 2. Shell 创建子进程
> 3. 子进程调用系统调用（比如 `open`、`read`、`getdents`）
> 4. **内核真正去读硬盘、查文件、返回结果**
> 5. 结果返回给子进程
> 6. 子进程打印到屏幕
> 7. Shell 继续等待下一条命令

# 02 一条 Shell 命令的完整运行流程

## 2.1 总流程：读取 → 解析 → 查找 → 执行 → 返回

一条命令从输入到执行完成，大致经历以下过程：

```text
用户输入命令
    ↓
Shell 从终端读取命令
    ↓
Shell 解析命令：命令名、参数、引号、通配符、变量、重定向、管道
    ↓
判断命令类型：别名 / 关键字 / 函数 / 内置命令 / 外部命令
    ↓
执行命令：内置命令在当前 Shell 执行；外部命令 fork + exec
    ↓
等待命令结束，得到退出状态码
    ↓
输出结果到 stdout/stderr
```

| 特性                    | 内置命令                                    | 外部命令                                     |
| ----------------------- | ------------------------------------------- | -------------------------------------------- |
| **执行主体**            | Shell 本身直接执行                          | 单独的可执行文件，由 Shell 启动子进程执行    |
| **执行速度**            | 极快（不需要创建新进程）                    | 较慢（需要磁盘 IO + 创建子进程）             |
| **存在位置**            | 内嵌在 Shell 程序里，无独立文件             | 存放在磁盘上（如 `/usr/bin/`、`/bin/` 目录） |
| **是否影响 Shell 本身** | 直接修改 Shell 的状态（如 `cd` 改当前目录） | 不影响 Shell 状态，仅在子进程内生效          |
| **典型例子**            | `cd`、`pwd`、`alias`、`history`             | `ls`、`grep`、`cat`、`mkdir`                 |

```sh
# 判断 cd
$ type cd
cd is a shell builtin  # 输出带 builtin，说明是内置命令

# 判断 ls
$ type ls
ls is aliased to `ls --color=auto'
/usr/bin/ls  # 输出了路径，说明是外部命令

# 判断 pwd
$ type pwd
pwd is a shell builtin
/usr/bin/pwd  # 有些命令同时有内置和外部版本
```

> 核心规律：**和 Shell 自身状态相关的，基本都是内置命令**（比如改目录、改环境变量、看历史记录）；和文件、进程操作相关的，大多是外部命令。

## 2.2 第一步：读取命令

当你输入：

```bash
ls -l /home
# 或
grep "error" app.log > result.txt 2>&1
```

Shell 会从标准输入 `stdin` 读取这行文本。标准输入通常来自键盘，也可以来自文件或管道。

Linux 中有三个默认文件描述符：

| 文件描述符 | 名称   | 含义     | 默认连接  |
| ---------- | ------ | -------- | --------- |
| `0`        | stdin  | 标准输入 | 终端/键盘 |
| `1`        | stdout | 标准输出 | 终端/屏幕 |
| `2`        | stderr | 标准错误 | 终端/屏幕 |

> **为什么 `>` 前面一般不写 `1`？**
>
> 因为 Shell 规定：
>
> ```
> command > file
> ```
>
> 默认就是：
>
> ```
> command 1> file
> ```
>
> 所以：
>
> ```
> grep "error" app.log > result.txt
> ```
>
> 和：
>
> ```
> grep "error" app.log 1> result.txt
> ```
>
> 完全一样。
>
> 可以理解成：
>
> ```
> 原本：
> 
> 0 stdin   ← 键盘
> 1 stdout  → 终端
> 2 stderr  → 终端
> 
> 
> 执行：
> 
> grep "error" app.log 1> result.txt
> 
> 
> 变成：
> 
> 0 stdin   ← 键盘
> 1 stdout  → result.txt   ← 只有 1 被修改了
> 2 stderr  → 终端         ← 没动，所以保持默认
> ```

## 2.3 第二步：解析命令

Shell 不会把整行命令原封不动执行，而是会做解析。以这条命令为例：

```bash
ls -l /home
```

解析结果：

| 部分 | 含义 |
|---|---|
| `ls` | 命令名 |
| `-l` | 选项，表示长格式显示 |
| `/home` | 参数，表示要查看的目录 |

再看复杂一点的：

```bash
grep "error" app.log > result.txt 2>&1 # &表明后面的 1 是文件描述符（数字），不是文件名！
# 2 > 1 ：意思是：把错误输出到一个叫做 “1” 的文件里（会生成一个叫 1 的文件）
# 输出重定向：echo "hello" > a.txt，本来 echo 要把 "hello" 输出到终端，现在把输出方向改到 a.txt。
# 输入重定向：程序本来可能从键盘/终端读取输入，现在你告诉 Shell：别从键盘读取了，从这个文件读取。 如 sort < numbers.txt
# 程序 > 文件 即 程序 -> 文件 就是输出重定向
# 程序 < 文件 即 程序 <- 文件 就是输入重定向
# >    输出重定向，并覆盖原内容
# >>   输出重定向，并追加到末尾
# <    输入重定向，从文件获取输入
```

Shell 会解析出：

| 部分 | 含义 |
|---|---|
| `grep` | 命令名 |
| `"error"` | 搜索关键字，双引号保护空格和特殊字符 |
| `app.log` | 输入文件 |
| `> result.txt` | 标准输出重定向到 `result.txt` |
| `2>&1` | 标准错误也重定向到标准输出当前指向的位置，即让 `2` 指向 `1` **现在指向的地方**。 |

> 1. **grep 找出来的 error**
>
>    = 日志里的文字
>
>    = **正常输出（1）**
>
>    - `echo`：**把指定的内容输出出来**，通常输出到终端。
>    - `grep`：**在文本中搜索符合条件的内容**，通常按“行”查找。
>
> 2. **2>&1 捕获的错误**
>
>    = grep 命令自己的报错：比如文件找不到
>
>    = **真正的错误（2）**
>    
>    其中执行 > result.txt （等价于1> result.txt）后：
>    
>    stdout（1） ──────────→ result.txt
>    stderr（2） ──────────→ 终端
>    
>    紧接着：2>&1 即**让标准错误 2，也去标准输出 1 当前正在去的地方。**
>    
>    1 stdout ───→ result.txt
>                     ↑
>    2 stderr ────────┘

## 2.4 第三步：判断命令类型

Shell 会按一定优先级判断命令属于哪一类。常见类型如下：

> **内置命令（builtin）是 Shell 自己会执行的功能；外部命令（external）是 Shell 去启动另一个程序来执行。**

| 类型 | 说明 | 例子 |
|---|---|---|
| alias 别名 | 用户定义的命令缩写 | `ll='ls -l'` |
| keyword 关键字 | Shell 语法的一部分 | `if`、`then`、`for`、`while` |
| function 函数 | Shell 函数 | `my_backup(){ ...; }` |
| builtin 内置命令 | Shell 自带命令 | `cd`、`pwd`、`history`、`alias` |
| external 外部命令 | 文件系统中的可执行文件 | `/usr/bin/ls`、`/usr/bin/grep` |

cd   → 我自己会
grep → 我需要运行 /usr/bin/grep 这个程序

查看命令类型最推荐使用：

```bash
type cd
type ls
type -a ls
```

`type -a` 会列出一个命令可能对应的所有解释，例如别名和真实可执行文件。

`which` 也能查找命令路径，但它通常只适合查外部命令，不一定能完整反映别名、函数、内置命令。

```bash
which ls
command -v ls
```

常用建议：

| 命令 | 推荐程度 | 原因 |
|---|---|---|
| `type 命令` | 高 | 能识别内置命令、别名、函数、外部命令 |
| `command -v 命令` | 高 | 脚本中更常用，适合判断命令是否存在 |
| `which 命令` | 中 | 主要查外部命令路径，不适合解释所有 Shell 语义 |

> 为什么需要分成内置和外部？因为有些命令**必须由 Shell 自己执行**。
>
> 最典型的就是 `cd`。
>
> 假设 `cd` 是一个外部程序：
>
> ```
> Shell 当前目录：/home
> 
> Shell
>  ↓
> 启动一个 cd 程序
>  ↓
> cd 程序把“自己的目录”改成 /test
>  ↓
> cd 程序结束
>  ↓
> Shell 还是在 /home
> ```

## 2.5 第四步：PATH 查找外部命令

外部命令本质上是磁盘上的可执行文件。例如 `ls` 通常位于：

```bash
/usr/bin/ls
```

当你输入：

```bash
ls
```

Shell 会根据环境变量 `PATH` 到一组目录里依次查找叫 `ls` 的可执行文件。

查看 PATH：

```bash
echo $PATH
```

典型输出类似：

```bash
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
即6个目录
/usr/local/sbin
/usr/local/bin
/usr/sbin
/usr/bin
/sbin
/bin
```

冒号 `:` 用来分隔多个目录。Shell 会从左到右查找。

> 你输入 `ls`，Shell 会做什么？
>
> 1. 先看 `ls` 是不是**内置命令**（不是）
> 2. 然后去 `PATH` 里的目录里找：
>    - 先找 `/usr/local/sbin` 里有没有 `ls`
>    - 再找 `/usr/local/bin` 里有没有 `ls`
>    - 再找 `/usr/sbin` 里有没有 `ls`
>    - 再找 `/usr/bin` 里有没有 `ls`（找到了！`/usr/bin/ls`）
> 3. 找到后就执行这个程序。
>
> `echo $PATH` 就是把这张「查找地图」打印出来，让你看到 Shell 会去哪些目录里找命令。

如果当前目录下有一个脚本 `hello.sh`，直接输入 `hello.sh` 可能执行不了，因为当前目录 `.` 通常不在 PATH 中。应该写：

```bash
./hello.sh
```

这里 `./` 表示当前目录。

## 2.6 第五步：内置命令在当前 Shell 执行

`cd` 必须是内置命令，因为当前工作目录是进程自己的属性。假设 `cd` 放到子进程里执行，那么子进程切换目录后退出，父进程 Shell 的目录不会改变，用户就会感觉 `cd` 没有生效。

验证 `cd` 是内置命令：

```bash
type cd
```

可能输出：

```bash
cd is a shell builtin
```

## 2.7 第六步：外部命令通常 fork + exec + wait

对于外部命令，Shell 通常执行如下流程：

```text
Shell 父进程
    ↓ fork()
创建子进程
    ↓ exec()
子进程加载外部程序，例如 /usr/bin/ls
    ↓
程序运行结束
    ↓ exit()
子进程退出
    ↓ wait()
Shell 父进程等待并回收子进程状态
```

核心系统调用理解：

| 调用 | 作用 | 类比 |
|---|---|---|
| `fork()` | 复制当前进程，创建子进程 | 复制一个“分身” |
| `exec()` | 用新程序替换当前进程内容 | 分身换上另一个程序的身体 |
| `wait()` | 父进程等待子进程结束并获取状态 | 等员工交付结果 |
| `exit()` | 进程退出并返回状态码 | 员工完成任务离场 |

> 1. **`fork()`：老板复制一个「分身」（创建子进程）**
>
> **作用**：复制当前 Shell 进程，生成一个一模一样的「子进程」
>
> **比喻**：老板为了不亲自干活，复制了一个和自己完全一样的分身，专门去处理任务。
>
> - 复制出来的子进程，一开始和父进程（Shell）长得一模一样：同一个程序、同一个环境变量、同一个当前目录
> - 唯一的区别是 PID（进程 ID）不一样，父子进程从此分道扬镳
>
> 2. **`exec()`：分身「变身」成命令程序**
>
> **作用**：把子进程里的程序，替换成外部命令的可执行文件（比如 `/usr/bin/ls`）
>
> **比喻**：分身拿到任务后，立刻把自己的 “老板身份” 换成 “工具人身份”，开始执行 `ls` 这个程序。
>
> - 原来的 Shell 代码会被完全替换，变成 `ls` 的机器指令
> - 进程 ID 不变，但是里面的程序已经变了，相当于 “借壳上市”
>
> 3. **`程序运行`：工具人开始干活**
>
> **作用**：`ls` 程序执行它的逻辑，比如读取目录、列出文件，输出结果
>
> **比喻**：工具人开始执行任务，把结果打印出来。
>
> 4. **`exit()`：工具人干完活，主动退场**
>
> **作用**：子进程执行完后，调用 `exit()` 退出，并返回一个状态码（0 表示成功，非 0 表示失败）
>
> **比喻**：员工完成任务，给老板交了一份 “任务完成报告”（状态码），然后下班消失。
>
> 5. **`wait()`：老板等员工交差，回收状态**
>
> **作用**：父进程（Shell）调用 `wait()`，等待子进程退出，并获取它的退出状态码
>
> **比喻**：老板在原地等着，直到员工交回报告，确认任务完成情况，再继续处理下一个命令。
>
> - 如果没有 `wait()`，子进程退出后会变成「僵尸进程」，占着系统资源
> - `wait()` 就是 Shell 用来 “回收员工” 的操作，避免系统里堆一堆僵尸进程

> 当子进程调用 `exit()` 时，它只是：
>
> - 停止运行程序
> - 释放了大部分内存资源
> - 给内核留下了**退出状态码**（比如 0 表示成功，非 0 表示失败）
>
> 但它**并没有从系统里彻底消失**！
>
> 内核会保留它的一小部分信息（比如 PID、退出状态码），等着父进程来 “认领”。

## 2.8 第七步：命令返回结果和退出状态码

命令执行完成后会返回退出状态码。查看上一条命令状态码：

```bash
echo $?
```

约定：

| 状态码 | 含义 |
|---|---|
| `0` | 成功 |
| 非 `0` | 失败或异常 |
| `1` | 一般错误 |
| `2` | 命令使用错误或参数错误，具体看命令实现 |
| `126` | 找到命令但无法执行，例如没有执行权限 |
| `127` | 命令不存在 |
| `128 + n` | 被信号 n 终止，例如 Ctrl+C 常见为 130 |

示例：

```bash
ls file.txt
echo $?

ls not_exist.txt
echo $?
```

## 2.9 面试高频题：为什么 `cd` 是内置命令，`ls` 通常是外部命令？

**参考回答：**  
`cd` 修改的是当前 Shell 进程的工作目录，如果放到子进程中执行，子进程退出后不会影响父进程 Shell，所以必须由当前 Shell 自己执行，因此是内置命令。`ls` 只是读取目录内容并输出，不需要改变当前 Shell 的状态，所以可以作为外部可执行程序运行。

## 2.10 面试高频题：`fork()` 和 `exec()` 的区别是什么？

**参考回答：**  
`fork()` 用来创建子进程，子进程初始时几乎是父进程的副本；`exec()` 用来在当前进程中加载并运行一个新的程序，执行成功后原来的程序代码会被替换。Shell 执行外部命令时，一般先 `fork()` 创建子进程，再在子进程中 `exec()` 外部命令，父进程通过 `wait()` 等待子进程结束。

> #### 协同工作流程（以执行 ls 为例）：
>
> 1. **初始状态**：
>    您的终端里运行着一个 Shell 进程（假设进程 ID **PID = 100**）。
> 2. **用户输入 ls**：
>    Shell 发现 ls 是一个外部命令，于是调用 fork()。
> 3. **克隆出子进程**：
>    系统创建了一个子进程（**PID = 101**），它此时也是一个 Shell 进程，内容和父进程（PID 100）一模一样。
> 4. **兵分两路**：**子进程 (PID 101)**：立刻调用 exec("/bin/ls")。子进程的 Shell 代码被抹去，变身成了 /bin/ls 程序开始运行。**父进程 (PID 100)**：调用 wait() 挂起自己，进入休眠状态，等待子进程干完活。
> 5. **收尾**：
>    子进程（PID 101，现在的 ls）把目录内容打印到屏幕上，然后运行结束，正常退出。
> 6. **唤醒父进程**：
>    父进程（PID 100）收到子进程退出的信号，从 wait() 中醒来，重新打印出命令提示符（如 $），等待你的下一个命令。

| 特性               | fork()                                                     | exec()                                  |
| ------------------ | ---------------------------------------------------------- | --------------------------------------- |
| **主要目的**       | 创建一个新进程。                                           | 运行一个新程序。                        |
| **进程 ID（PID）** | 创建一个**全新的 PID** 给子进程。                          | **保持当前的 PID 不变**。               |
| **内存空间**       | **复制**父进程的内存空间。                                 | **覆盖/替换**当前进程的内存空间。       |
| **函数返回**       | 调用一次，返回两次（父进程返回子进程 PID，子进程返回 0）。 | 成功后**不返回**（只有失败时返回 -1）。 |
| **关系**           | 父子进程同时存在，并发运行。                               | 旧程序消失，新程序接管。                |

### 3.3.1 管道的关键细节

| 细节 | 说明 |
|---|---|
| 管道只连接 stdout | 默认只把前一个命令的标准输出传给后一个命令 |
| stderr 不会默认进入管道 | 错误输出仍然显示在屏幕，除非使用 `2>&1` 或 `|&` |
| 管道两侧通常是不同进程 | 每个命令一般在独立进程中执行 |
| 管道适合流式处理 | 前面边输出，后面边处理，不一定等前面全部结束 |

示例：把错误也交给管道处理：

```bash
find / -name "test" 2>&1 | grep "Permission denied"
```

或者 bash 中：

```bash
find / -name "test" |& grep "Permission denied"
```

## 3.4 重定向：改变输入输出位置

重定向不是把命令连起来，而是改变命令的输入/输出去向。

| 写法 | 含义 |
|---|---|
| `>` | 标准输出覆盖写入文件 |
| `>>` | 标准输出追加写入文件 |
| `<` | 从文件读取标准输入 |
| `2>` | 标准错误覆盖写入文件 |
| `2>>` | 标准错误追加写入文件 |
| `&>` | stdout 和 stderr 都写入文件，bash 常用 |
| `2>&1` | 把 stderr 重定向到 stdout 当前指向的位置 |
| `/dev/null` | 黑洞文件，丢弃输出 |

示例 1：覆盖写入

```bash
ls -l > files.txt
```

示例 2：追加写入

```bash
echo "hello" >> files.txt
```

示例 3：错误输出写入日志

```bash
ls not_exist.txt 2> error.log
```

示例 4：正常输出和错误输出都写入同一个文件

```bash
bash demo.sh > demo.log 2>&1
```

或者：

```bash
bash demo.sh &> demo.log
```

## 3.5 重定向顺序为什么重要

这两个命令不一样：

```bash
cmd > out.log 2>&1
cmd 2>&1 > out.log
```

第一条：

```text
1. stdout 指向 out.log
2. stderr 指向 stdout 当前的位置，也就是 out.log
结果：stdout 和 stderr 都进 out.log
```

第二条：

```text
1. stderr 指向 stdout 当前的位置，也就是屏幕
2. stdout 指向 out.log
结果：stdout 进 out.log，stderr 仍然在屏幕
```

记忆：`2>&1` 的意思是“让 2 指向 1 当前指向的位置”，不是永远跟踪 1。

## 3.6 输入重定向 `<`

```bash
wc -l < file.txt
```

含义：把 `file.txt` 内容作为 `wc -l` 的标准输入。

> **Word Count**（字数统计）的缩写。它的主要功能是**统计一个文件（或输入流）中的行数、单词数、以及字节数/字符数**。

对比：

```bash
wc -l file.txt
wc -l < file.txt
```

第一种输出通常带文件名，第二种只有行数，因为第二种是从 stdin 读入。

> **第一种写法：wc -l file.txt**
>
> - **原理**：你把文件名直接作为参数传给 wc。wc 亲自去打开这个文件，因此它**知道这个文件的名字**。
> - **输出**：10 file.txt （包含行数和文件名）。
>
> **第二种写法：wc -l < file.txt**
>
> - **原理**：这是**输入重定向**。Shell（终端）替 wc 打开了文件，并把文件里的内容像倒水一样，顺着标准输入（stdin）灌给了 wc。
> - **wc 懵逼的处境**：此时的 wc 就像是被蒙上了眼睛。它只知道有人往它的“嘴里”（输入流）灌进了一堆文本，它默默数了一下有 10 行。但**它完全不知道这些文本是从哪个文件来的**。
> - **输出**：10 （只有孤零零的行数，无法打印文件名）。

### 3.9.1 shebang 是什么

脚本第一行常见写法：

```bash
#!/bin/bash
```

它告诉系统：这个脚本应该交给 `/bin/bash` 来解释执行。如果写成：

```bash
#!/bin/sh
```

就表示交给 `/bin/sh` 解释，语法兼容性要求更严格。面试时可以说：shebang 决定脚本使用哪个解释器。

> **Shebang（#!）是什么？**
>
> 你可以把它理解为**“指定翻译官”**。
>
> 在 Windows 里，如果你双击一个 .docx 文件，系统会自动调用 Word 软件打开它，因为系统是通过“文件后缀名”来识别的。
>
> 但是在 Linux 里，**文件后缀名（如 .sh）只是个摆设**，系统根本不看它。那系统怎么知道这是一个 Shell 脚本，还是一个 Python 脚本呢？
> 它靠的就是文件第一行的 **Shebang**（也就是 #!）。
>
> - 当你运行一个脚本时，Linux 系统会先看第一行。
> - 如果第一行是 #!/bin/bash：系统就会说：“噢！这是一个 **Bash 脚本**，我得去调用 /bin/bash 这个程序来当翻译官，执行后面的代码。”
> - 如果第一行是 #!/usr/bin/python3：系统就会说：“噢！这是一个 **Python 脚本**，我得调用 Python 解释器来运行它。”
>
> > **#!/bin/bash 和 #!/bin/sh 的区别**：
> > bash 是现代的、功能更丰富的翻译官；sh 是古老的、功能简陋但兼容性极好的翻译官。日常开发中，我们绝大多数时候都用 #!/bin/bash。

### 3.9.2 三种脚本执行方式的区别

| 执行方式 | 是否需要执行权限 | 是否影响当前 Shell | 说明 |
|---|---:|---:|---|
| `bash script.sh` | 不需要 | 不影响 | 新开 bash 子进程执行 |
| `./script.sh` | 需要 | 不影响 | 按 shebang 指定解释器执行 |
| `source script.sh` | 不需要 | 会影响 | 在当前 Shell 执行，常用于加载环境变量 |

> `demo.sh` 没有执行 `x` 权限，`bash demo.sh` 仍然可以运行，只要 Bash 对这个文件有读取权限。
>
> 启动 `bash` 程序 → 让 Bash 读取 `demo.sh` → 执行里面的 Shell 命令。
>
> 如果你直接：
>
> ```
> ./demo.sh
> ```
>
> 这就完全不一样了。这句话是在说：
>
> > **我要直接执行 `demo.sh` 这个文件。**
>
> 既然你要“直接执行这个文件”，Linux 就会检查：
>
> ```
> demo.sh 有没有执行权限 x？
> ```

**`bash demo.sh` = 执行的是 bash，bash 去“读” demo.sh。**

**`./demo.sh` = 直接执行 demo.sh 本身。**

例如：

```bash
source ~/.bashrc
```

之所以使用 `source`，是因为我们希望 `.bashrc` 中的变量、函数、别名影响当前终端。

> **三种脚本执行方式的区别**
>
> 这三种执行方式，其实就是**接水管（进程控制）和权限要求**的区别。
>
> 还记得我们最开始讨论的 **“为什么 cd 是内置命令，而不能在子进程里执行”** 吗？这个表格讲的正是这个原理！
>
> **方式 1：bash script.sh**
>
> - **怎么理解**：你手动请出了 bash 这个翻译官，把脚本递给它，让它帮你读。
> - **为什么不需要权限**：因为你直接运行的是 bash 程序（它本身就有执行权限），脚本文件只是作为它的“阅读材料”。
> - **是否影响当前 Shell**：**不影响**。它会启动一个**子进程**去运行。如果脚本里写了 cd /tmp，运行完后，你当前终端的目录**不会**发生改变。
>
> **2. 方式 2：./script.sh**
>
> - **怎么理解**：你把脚本本身当成一个安装好的“APP（可执行程序）”，直接去双击运行它。
> - **为什么需要权限**：因为你是直接运行脚本文件，所以 Linux 的安全机制强制要求这个文件必须拥有“可执行权限”（也就是必须先执行 chmod +x script.sh）。
> - **它是怎么运行的**：系统运行它时，会去读取第一行的 **Shebang**，找到对应的翻译官，然后在一个**新开的子进程**里运行。同样，它**不影响**当前 Shell。
>
> **3. 方式 3：source script.sh（或者 . script.sh）**
>
> - **怎么理解**：你对当前的终端（父进程）说：“**别新开子进程了，就在你自己的肚子里，把这个脚本里的命令一行行执行了吧！**”
> - **为什么不需要权限**：因为是当前终端直接读取文件内容并执行，所以不需要可执行权限。
> - **是否影响当前 Shell**：**会影响**！因为是在当前进程中执行。如果脚本里写了 cd /tmp，执行完后，你当下的终端目录**真的会变成 /tmp**！


## 3.10 本部分面试/笔试题

### 题 1：管道和重定向有什么区别？

**答案：** 管道 `|` 连接两个命令，把前一个命令的标准输出作为后一个命令的标准输入；重定向改变一个命令的输入输出位置，例如输出到文件或从文件读取。管道强调命令之间传递数据，重定向强调命令与文件/设备之间改变输入输出方向。

### 题 2：把 `demo.sh` 的标准输出和标准错误都写入 `demo.log`，哪些写法正确？

```text
A. bash demo.sh &> demo.log
B. bash demo.sh < demo.log
C. bash demo.sh > demo.log 2>&1
D. bash demo.sh 2> demo.log 1> demo.log
```

**答案：A、C。**  
`&>` 是 bash 中把 stdout 和 stderr 同时写入文件；`> demo.log 2>&1` 先让 stdout 指向文件，再让 stderr 指向 stdout 当前的位置，因此二者都进入文件。`< demo.log` 是输入重定向。D 虽然两个都写同一文件，但 stdout/stderr 分别打开文件，可能覆盖或顺序异常，实际不推荐。

> `&>` 你可以直接理解成一个**简写**：
>
> > **把标准输出 `1` 和标准错误 `2`，全部重定向到同一个地方。**
>
> bash demo.sh &> demo.log 其中的 demo.sh 运行产生：
>
> 正常输出（1） ──┐
>                ├──→ demo.log
> 错误输出（2） ──┘

> 解释：看起来像是
>
> bash demo.sh 2> demo.log 1> demo.log 
> │            │           │
> │            │           └→ 正常输出1 → demo.log
> │            │
> │            └→ 错误输出2 → demo.log
> │
> └→ 用 Bash 执行 demo.sh

> D选项表面看：
>
> ```
> bash demo.sh 2> demo.log 1> demo.log
> ```
>
> 确实像是：
>
> ```
> 错误 2 ──→ demo.log
> 正常 1 ──→ demo.log
> ```
>
> 那不就完事了吗？
>
> **问题就在于：这两个 `>` 是分别打开 `demo.log` 的。**
>
> 假设 `demo.sh` 是：
>
> ```
> echo "正常信息"
> ls 不存在的文件
> echo "正常信息2"
> ```
>
> 它本来应该按顺序产生：
>
> ```
> 正常信息
> 错误信息
> 正常信息2
> ```
>
> 现在写：
>
> ```
> bash demo.sh 2> demo.log 1> demo.log
> ```
>
>
> 注意是先处理 2>，再处理 1>，最后才运行 demo.sh
>
> Shell 做的是：
>
> ```
> 2> demo.log
>    ↓
> 打开 demo.log 给 2 使用
> 
> 1> demo.log
>    ↓
> 又打开一次 demo.log 给 1 使用
> ```
>
> 于是可以想象成出现了**两支笔同时在同一本文件上写，而且各自有自己的“写到哪里了”的位置**：
>
> ```
> 标准错误 2 ──→ [一支笔] ──┐
>                            ├→ demo.log
> 标准输出 1 ──→ [另一支笔] ──┘
> ```
>
> 两边可能互相覆盖。
>
> 例如错误先写：
>
> ```
> 错误：找不到文件
> ```
>
> 然后正常输出又从它自己的文件位置开始写：
>
> ```
> 正常信息
> ```
>
> 就可能把前面的部分内容覆盖掉。
>
> 所以问题不是：
>
> > `2>` 一定把 `1>` 覆盖掉。
>
> 而是：
>
> > **1 和 2 是分别打开同一个文件，各自维护写入位置，因此不应该用这种方式来“合并”两路输出。**

### 题 3：`cmd >log 2>&1` 和 `cmd 2>&1 >log` 一样吗？（cmd相当于数学中的未知数x，可以替换为真正的指令ls等）

**答案：不一样。**  
Shell 从左往右处理重定向，而 `2>&1` 的意思是：让 2 去“复制 1 此时的位置”。

第一种：`cmd >log 2>&1`，一开始：1 标准输出 → 屏幕，2 标准错误 → 屏幕

`>log`后：1 → log，2 → 屏幕 。`2>&1`后：2，你看看 **1 现在去哪儿**，你也去那里。最终两个都进 `log`。✅

第二种：先`2>&1`，1与2都指向屏幕 ，然后`>log`即将1改为log 但是此时2是屏幕

# 04 Linux 用户与用户组

## 4.1 为什么 Linux 要有用户和用户组

Linux 是多用户系统，一台服务器可能同时服务开发、测试、运维、数据库、Web 服务等多个身份。用户和用户组的作用是隔离权限：谁可以读文件，谁可以修改文件，谁可以执行程序，谁可以管理系统。

## 4.2 三类常见用户

| 类型 | 说明 | 例子 |
|---|---|---|
| root 用户 | 超级管理员，UID 为 0，权限最高 | `root` |
| 普通用户 | 日常登录、开发、运行命令 | `alice`、`bob` |
| 系统用户 | 给服务进程使用，一般不用于登录 | `nginx`、`mysql`、`www-data` |

查看当前用户：

```bash
whoami
```

查看用户 UID、GID、所属组：

```bash
id
id username
```

查看当前用户属于哪些组：

```bash
groups
```

## 4.3 用户和用户组相关文件

| 文件 | 作用 | 是否建议直接手改 |
|---|---|---|
| `/etc/passwd` | 用户基本信息：用户名、UID、GID、家目录、登录 Shell | 不建议 |
| `/etc/shadow` | 加密后的密码和密码策略 | 不建议 |
| `/etc/group` | 用户组信息 | 不建议 |
| `/etc/sudoers` | sudo 授权规则 | 必须用 `visudo` |

查看 root 用户信息：

```bash
grep '^root:' /etc/passwd
```

典型格式：

```text
root:x:0:0:root:/root:/bin/bash
```

字段含义：

```text
用户名:密码占位符:UID:GID:描述信息:家目录:登录Shell
```

## 4.4 su 和 sudo

| 命令 | 作用 | 需要什么密码 | 使用场景 |
|---|---|---|---|
| `su root` | 切换到 root 用户 | root 密码 | 完整切换身份 |
| `su - root` | 切换到 root 并加载 root 登录环境 | root 密码 | 更接近 root 真实登录 |
| `sudo command` | 以授权身份执行单条命令 | 当前用户密码 | 临时提权执行命令 |

推荐日常使用 `sudo`，少用长期 root Shell，避免误操作。

## 4.5 用户和组管理命令

| 命令 | 作用 |
|---|---|
| `useradd username` | 创建用户 |
| `passwd username` | 设置用户密码 |
| `userdel username` | 删除用户 |
| `usermod` | 修改用户属性 |
| `groupadd groupname` | 创建用户组 |
| `groupdel groupname` | 删除用户组 |
| `gpasswd -a user group` | 把用户加入组 |
| `id username` | 查看用户身份信息 |

示例：创建项目组和用户：

```bash
sudo groupadd project
sudo useradd -m -g project dev01
sudo passwd dev01
id dev01
```

`-m` 表示创建家目录，`-g project` 表示指定主组。

## 4.6 本部分面试题

### 题 1：root 用户为什么权限最大？

**答案：** Linux 中 UID 为 0 的用户拥有超级用户权限，通常用户名是 root。内核在权限检查时会特殊对待 UID 0，因此 root 可以绕过大部分普通权限限制，执行系统管理操作。也正因为 root 权限太高，生产环境通常通过 sudo 精细授权，避免长期使用 root。

### 题 2：`su - root` 和 `su root` 有什么区别？

**答案：** `su root` 切换用户但不完全加载目标用户的登录环境；`su - root` 会模拟 root 登录，加载 root 的环境变量、家目录等，更接近真正登录 root。排查环境变量问题时这个区别很重要。

> - **su root（不带减号 -）：半路换人，但行李没换**
>   - **含义**：你只是把自己的“身份牌”换成了 root，但你依然穿着原来的衣服、背着原来的背包（**保留了原用户的环境变量**），并且还站在原地（**当前工作目录不变**）。
> - **su - root（带减号 -）：彻底变身，全面接管含义**：你不仅换了 root 的身份牌，还把旧行李全部扔掉，换上了 root 的全套衣服和背包（**重新加载 root 的全部环境变量**），并且瞬间移动到了 root 的家门口（**工作目录切换到 /root**）。

# 05 文件/目录权限表示方法

## 5.1 `ls -l` 输出怎么看

执行：

```bash
ls -l file.txt
```

可能输出：

```text
-rw-r--r-- 1 alice dev 1234 Jan 11 10:00 file.txt
```

每一列含义：

| 列 | 示例 | 含义 |
|---|---|---|
| 第 1 列 | `-rw-r--r--` | 文件类型 + 权限 |
| 第 2 列 | `1` | 硬链接数 |
| 第 3 列 | `alice` | 所有者 |
| 第 4 列 | `dev` | 所属组 |
| 第 5 列 | `1234` | 文件大小，单位字节 |
| 第 6-8 列 | `Jan 11 10:00` | 修改时间 |
| 第 9 列 | `file.txt` | 文件名 |

## 5.2 第一位：文件类型

| 标识 | 含义 | 例子 |
|---|---|---|
| `-` | 普通文件 | 文本、日志、二进制程序 |
| `d` | 目录 | 文件夹 |
| `l` | 符号链接 | 软链接 |
| `c` | 字符设备 | 终端、串口等 |
| `b` | 块设备 | 磁盘设备 |
| `p` | 管道文件 FIFO | 进程间通信 |
| `s` | socket 文件 | 本地域套接字 |

示例：

```bash
ls -l /dev/null
ls -ld /tmp
ls -l /bin/sh
```

## 5.3 后九位：三组权限

以 `-rw-r--r--` 为例：

```text
-   rw-   r--   r--
│    │     │     │
│    │     │     └── 其他用户 others 权限
│    │     └──────── 所属组 group 权限
│    └────────────── 所有者 user 权限
└─────────────────── 文件类型
```

三组身份：

| 位置 | 英文 | 含义 |
|---|---|---|
| 第 1 组 | user / owner | 文件所有者 |
| 第 2 组 | group | 文件所属组内用户 |
| 第 3 组 | others | 其他用户 |

> 在一家互联网公司里，Linux 服务器上会运行着各种各样的程序（比如 Nginx、MySQL），同时也有很多不同职责的员工（比如前端开发、后端开发、运维、数据库管理员）。
>
> 我们来看看，**在实际工作里，为什么要大费周章地划分这 3 个身份，以及它们到底是怎么起作用的**。
>
> ------
>
> **1. 所有者（User / Owner）—— 作用：保障核心资产安全，防止“越权”**
>
> - **实际作用**：
>   在 Linux 中，很多核心软件和系统配置，必须指定给一个**唯一的、特定的账号**来管理，以防止被其他无关人员或程序乱动。
> - **真实例子：数据库密码文件****背景**：服务器上安装了 MySQL 数据库。数据库的账号密码存在 /etc/mysql/my.cnf 这个配置文件里。**权限设计**：**所有者（User）**：设为 mysql 用户。权限设为 **rw- --- ---**（只有所有者 mysql 能读写，其他人连看都不能看）。**为什么要这样？**
>   如果这个文件不指定特定的所有者，或者让其他人也能看，那么任何一个普通员工登录服务器，都能看到数据库密码，公司的数据资产就彻底泄露了。
>
> ------
>
> **2. 所属组（Group）—— 作用：实现“团队协作”，避免反复修改权限**
>
> - **实际作用**：
>   公司里往往是一个团队（比如 5 个前端开发）共同负责一个项目。如果每个人都用自己的账号，修改别人的文件就会提示“无权限”。
>   **“所属组”就是为了让这一个团队的人能够顺畅地合作，而不需要把超级管理员 root 的密码告诉他们。**
> - **真实例子：网页代码开发团队****背景**：公司有个官网，代码放在 /var/www/html 目录下。团队里有三个开发：小明、小红、小刚。**权限设计**：运维在系统里建一个叫 web_dev 的**工作组**。把小明、小红、小刚三个人的账号都加到 web_dev 组里。把 /var/www/html 文件夹的**所属组（Group）**设为 web_dev。文件夹的所属组权限设为 **rwx**（同组的人能读、能写、能进入）。**为什么要这样？**
>   这样一来，小明写完的代码，小红能直接上去修改，小刚也能继续完善。他们不需要共享同一个账号密码，每个人用自己的账号就能在同一个文件夹里愉快地干活。同时，公司的财务、行政人员虽然也能登录这台服务器，但因为他们不在 web_dev 组里，完全无法修改代码。
>
> ------
>
> **3. 其他人（Others）—— 作用：公共服务访问，或者彻底“拉黑”**
>
> - **实际作用**：
>   这里的“其他人”，通常不是指具体的某个人，而是指**那些既不是所有者，也不在工作组里的“公共程序”或者“无关人员”**。
>   我们要么允许他们进行最低限度的访问，要么彻底把他们关在门外。
> - **真实例子 1：Nginx 网页服务器（允许访问）****背景**：你写好了网页代码，放在 /var/www/html/index.html。你希望全世界的用户通过浏览器都能看到你的网页。**权限设计**：网页是由一个叫 nginx 的系统服务去读取并展示给用户的。这个 nginx 既不是代码所有者，也不在开发组里，对代码来说，它就是“其他人（Others）”。所以，代码文件的“其他人”权限必须保留 **r--（可读）**。**为什么要这样？**
>   如果把“其他人”的 r 权限给关掉（变成 ---），那么 nginx 服务就读不到这个网页，全球用户访问你的网站时，就会看到著名的 **403 Forbidden（拒绝访问）** 报错。
> - **真实例子 2：用户的私钥文件（彻底拉黑）****背景**：你登录服务器需要一个“私钥文件” id_rsa。这个文件如果被别人拿到，别人就能冒充你登录服务器。**权限设计**：权限必须设为 **rw- --- ---**。也就是把“所属组”和“其他人”的权限全部彻底抹去（---）。**为什么要这样？**
>   如果你的私钥文件允许“其他人”读取，Linux 系统检测到后，出于安全考虑，甚至会直接拒绝让你使用这个私钥登录，并报错警告：你的私钥太开放了，不安全！
>
> ------
>
> **🏁 一个完整的实战故事：**
>
> 把这三者串联起来，就是大厂里最真实的开发日常：
>
> 1. **小明（所有者）** 新写了一个网页，他拥有这个文件的绝对权力（rw-）。
> 2. **小红（同组室友）** 发现小明写的代码有个 Bug。因为网页文件属于 web_dev 组（rw-），小红直接登录自己的账号，把 Bug 改掉了。
> 3. **Nginx 网页服务器（其他人）** 每天要负责把这个网页展示给几百万网友。因为文件对“其他人”开放了只读（r--），Nginx 顺利读取了代码，网站运行非常完美。
> 4. **公司新来的实习生小李（不在组内的其他人）** 感到好奇，想去改这个网页代码。但他一打开，系统立刻弹出提示：Permission denied（权限拒绝）。*小李既不是小明，也不在 web_dev 组里，他是“其他人”，只有只读权限，无法乱改代码。*
>
> 这就是 Linux 权限系统的实际运转方式：**既保证了团队能高效协作，又防止了外行或黑客把系统搞崩溃，同时还能保证公共服务的正常运行。**

## 5.4 `rwx` 对普通文件的含义

| 权限 | 英文 | 对普通文件的含义 |
|---|---|---|
| `r` | read | 可以读取文件内容，例如 `cat file` |
| `w` | write | 可以修改文件内容，例如编辑保存 |
| `x` | execute | 可以把文件当程序执行，例如 `./script.sh` |

注意：普通文件有 `x` 权限不代表它一定能正确运行，还要看文件内容是否是有效脚本或二进制程序。

## 5.5 `rwx` 对目录的含义

| 权限 | 对目录的含义 | 没有会怎样 |
|---|---|---|
| `r` | 可以列出目录中文件名，例如 `ls dir` | 不能列出目录内容 |
| `w` | 可以在目录中创建、删除、重命名文件 | 不能改目录项 |
| `x` | 可以进入目录、访问目录中的文件元信息 | 不能 `cd dir`，不能访问目录下具体文件 |

目录中最关键的是 `x` 权限。没有 `x`，即使有 `r`，也很难真正访问里面的文件。

## 5.6 目录权限组合实验

| 目录权限 | 效果 |
|---|---|
| `r--` | 可以尝试列文件名，但无法进入，也无法查看详细属性 |
| `--x` | 不能列目录，但如果知道文件名，可以访问目录中的文件 |
| `r-x` | 可以进入并列出目录，但不能创建/删除文件 |
| `-wx` | 可以创建/删除已知名字的文件，但不能正常列出目录 |
| `rwx` | 可进入、可列出、可创建删除 |

重点：删除一个文件，主要看你对它的 **父目录** 有没有 `w+x` 权限，而不是看文件本身有没有 `w` 权限。

## 5.7 权限的数字表示法

| 权限 | 数字 |
|---|---:|
| `r` | 4 |
| `w` | 2 |
| `x` | 1 |
| `-` | 0 |

每组三位相加：

| 字符 | 数字 | 含义 |
|---|---:|---|
| `---` | 0 | 无权限 |
| `--x` | 1 | 执行/进入 |
| `-w-` | 2 | 写 |
| `-wx` | 3 | 写 + 执行 |
| `r--` | 4 | 读 |
| `r-x` | 5 | 读 + 执行 |
| `rw-` | 6 | 读 + 写 |
| `rwx` | 7 | 读 + 写 + 执行 |

常见权限：

| 数字 | 字符 | 常见用途 |
|---|---|---|
| `644` | `rw-r--r--` | 普通文本文件 |
| `600` | `rw-------` | 私钥、敏感配置 |
| `755` | `rwxr-xr-x` | 目录、可执行脚本 |
| `700` | `rwx------` | 私有目录 |
| `664` | `rw-rw-r--` | 组内可写文件 |
| `775` | `rwxrwxr-x` | 组内协作目录 |
| `777` | `rwxrwxrwx` | 所有人可写，非常危险，慎用 |

> **坑一：为什么我没有文件的写权限，甚至文件是 root 的，我却能把它删了？**
>
> > /home 目录权限是 777（所有人可读写执行）。root 用户在里面创建了一个文件 root.c，正常情况下普通用户对这个文件只有只读权限（r--），**但用户却能用 rm 命令把 root.c 成功删掉！**
>
> **1. 核心秘密：删除一个文件，到底是在修改谁？**
>
> 很多人直觉上认为：“要删除一个文件，我得对这个**文件**有写权限。”
> **大错特错！**
>
> 在 Linux 的底层文件系统中：
>
> - **文件本身**：只存放数据内容（比如代码、文字）。
> - **目录（文件夹）**：本质上也是一个文件，里面存的是一张**“文件名 `→→` 节点号（inode）”的对照表**。
>
> > 💡 **“纸箱与纸条”的比喻**：
> > 想象一下，/home 目录是一个**纸箱**，而 root.c 是纸箱里的一张**纸条**。
> >
> > - 纸条上写着绝密机密，并且被胶水封死了，你打不开也改不了（也就是说，你对**文件**没有写/改权限）。
> > - 但是，这个纸箱是你的，或者你有权往纸箱里放东西、扔东西（也就是说，你对**目录**有写 w 权限）。
> > - 你虽然改不了纸条上的字，但你嫌它碍眼，**直接把整张纸条从纸箱里拿出来，扔进垃圾桶烧了。**
>
> **结论**：在 Linux 中，**删除一个文件，本质上是在修改“父目录文件”里的对照表**（把文件名那一行删掉）。所以，**能不能删除一个文件，完全取决于你对该文件“所在的目录”有没有写（w）权限！与你对该文件本身有没有权限、文件是谁的，没有任何关系！**
>
> ------
>
> **坑一的解决方案：粘滞位（Sticky Bit，用 t 表示）**
>
> 上面的机制虽然符合底层逻辑，但实际很不安全：如果一个部门共享一个文件夹（权限设为 777），那调皮的实习生岂不是可以把主管写的核心代码全部删光？
>
> 为了解决这个“不科学”的问题，Linux 引入了**粘滞位（Sticky Bit）**：
>
> - **作用**：如果一个目录被设置了粘滞位，那么**在这个目录下的文件，只有“文件所有者”或者“超级管理员 root”才能删除它**，其他人就算对目录有 w 权限，也无法删除别人的文件。
> - **符号表示**：在其他人权限的 x 位置上，会变成 **t**（比如 drwxrwxrwt）。
> - **数字表示**：在 777 前面加一个 1，即 **1777**（chmod 1777 /home）。
>
> > 📂 **现实生活中的例子**：
> > Linux 系统的 **/tmp** 目录（存放临时文件的地方）。所有人都可以往里面写文件，但为了防止大家互相乱删，/tmp 默认的权限就是 **drwxrwxrwt**（带粘滞位 t）。
>
> ------
>
> **坑二：目录的 r（读）和 x（执行）到底有什么区别？**
>
> 这是另一个极容易混淆的地方。很多人以为“只要有了读 r 权限，我就可以看里面的文件”。**并不是！**
>
> 对于**目录**而言：
>
> - **r (Read)**：代表你能否**列出**里面的文件名（即运行 **ls**）。
> - **x (Execute)**：代表你能否**穿过/进入**这个目录（即运行 **cd**，以及**访问目录里面的文件内容**）。
>
> 我们来看两种极端情况，这就很容易懂了：
>
> **情况 A：目录只有 r，没有 x（有读无执行）**
>
> 假设一个目录权限是 dr--r--r--：
>
> 1. **你可以运行 ls**：你会看到里面有 a.txt、b.txt。
> 2. **你无法 cd 进去**：系统会提示 Permission denied。
> 3. **你无法读取里面文件的内容**：比如你运行 cat a.txt，系统依然提示 Permission denied！*为什么？* 因为要读取 a.txt，系统必须通过该目录去寻找 a.txt 的底层数据。你没有 x（执行）权限，系统就无法“穿过”这个目录去触碰里面的文件。
>
> **情况 B：目录只有 x，没有 r（有执行无读）**—— 俗称“暗房模式”
>
> 假设一个目录权限是 d--x--x--x：
>
> 1. **你无法运行 ls**：你无法查看这个目录里到底有哪些文件，系统提示 Permission denied。
> 2. **你可以 cd 进去**：你可以成功进入这个目录。
> 3. **如果你知道文件名，你可以直接精准访问它！**比如你事先知道里面有一个叫 secret.txt 的文件，你直接运行 cat secret.txt，**只要你对 secret.txt 文件本身有读权限，你就能成功看到内容！***比喻*：这就像一间完全漆黑的房间（没有 r，你看不到有什么），但只要你进去后（有 x），凭记忆摸到了桌子上的杯子（知道文件名），你依然可以使用这个杯子。
>
> ------
>
> **总结备忘表**
>
> 为了在以后工作中达到“精通”不翻车，请牢记这张表：
>
> | 你想做的动作         | 对应 Linux 命令    | **对“父目录”**需要的权限                      | **对“文件本身”**需要的权限    |
> | -------------------- | ------------------ | --------------------------------------------- | ----------------------------- |
> | **进入目录**         | cd /dir            | **x**                                         | —                             |
> | **看目录里有什么**   | ls /dir            | **r** (最好有 x)                              | —                             |
> | **在目录里新建文件** | touch /dir/new.txt | **w** + **x**                                 | —                             |
> | **删除/重命名文件**  | rm /dir/old.txt    | **w** + **x**（若有粘滞位，还必须是文件主人） | —（**不需要文件本身的权限**） |
> | **看文件内容**       | cat /dir/old.txt   | **x**                                         | **r**                         |
> | **改文件内容**       | vim /dir/old.txt   | **x**                                         | **w**                         |

## 5.8 本部分面试题

### 题 1：`-rw-r--r--` 表示什么？对应数字是多少？

**答案：** 第一位 `-` 表示普通文件；后面九位分成三组：所有者 `rw-`，所属组 `r--`，其他用户 `r--`。表示所有者可读可写不可执行，组用户和其他用户只读。数字权限是 `644`。

### 题 2：为什么有时候文件本身没有写权限，却还能被删除？

**答案：** 删除文件本质上是修改父目录的目录项，而不是修改文件内容。因此能不能删除一个文件，主要看用户对该文件所在的父目录是否有 `w+x` 权限。如果对父目录有写和执行权限，即使文件本身是只读，也可能删除它。粘滞位目录除外，例如 `/tmp` 会限制普通用户删除别人的文件。

# 06 权限修改命令：chmod、chown、chgrp

## 6.1 chmod：修改权限

`chmod` 用于修改文件或目录权限。

```bash
chmod 权限 文件或目录
```

两种写法：

| 写法 | 示例 | 说明 |
|---|---|---|
| 数字模式 | `chmod 644 file.txt` | 简洁，最常用 |
| 字符模式 | `chmod u+x file.txt` | 局部增删权限，适合精细修改 |

## 6.2 chmod 数字模式

```bash
chmod 644 file.txt
chmod 755 script.sh
chmod 700 private_dir
```

`755` 表示：

```text
7 = rwx = 所有者可读可写可执行
5 = r-x = 所属组可读可执行
5 = r-x = 其他用户可读可执行
```

## 6.3 chmod 字符模式

格式：

```bash
chmod [用户范围][操作符][权限] 文件
```

用户范围：`u` 所有者，`g` 所属组，`o` 其他用户，`a` 所有人。  
操作符：`+` 增加，`-` 删除，`=` 覆盖设置。

示例：

```bash
chmod u+x script.sh      # 给所有者增加执行权限
chmod g-w file.txt       # 删除所属组写权限
chmod o-r file.txt       # 删除其他用户读权限
chmod a+r file.txt       # 所有人增加读权限
chmod u=rw,g=r,o= file   # 所有者读写，组只读，其他人无权限
```

## 6.4 chmod 递归修改 `-R`

```bash
chmod -R 755 mydir
```

> 在 Linux 中，大写的 **-R** 代表 **Recursive（递归）**。
>
> - **普通修改**：chmod 755 mydir 只会修改 mydir 这一个文件夹的权限，它里面的子文件、子文件夹的权限**完全不会变**。
> - **递归修改**：chmod -R 755 mydir 就像一个传染病。它不仅会把 mydir 改成 755，还会一路向下，把里面**所有的子文件夹、子文件、孙子文件夹……全部一刀切改成 755**。

危险点：不要随便对系统目录执行：

```bash
chmod -R 777 /
chmod -R 777 /usr
chmod -R 777 /etc
```

> **为什么对系统目录执行 chmod -R 777 是毁灭性灾难？**
>
> 很多新手在遇到“权限不足（Permission Denied）”报错时，由于图省事，脑子一热就会输入：
> sudo chmod -R 777 /etc 或者 sudo chmod -R 777 /
>
> 在运维界，这被称为**“从删库到跑路”级别的灾难操作**。一旦执行，服务器基本宣告报废，只能重装系统。原因有三点：
>
> **1. 核心安全程序会“直接罢工”**
>
> Linux 系统极其注重安全。很多核心安全工具在启动时，会**强制检查**自己的配置文件权限。如果发现权限太宽松（比如变成了 777），它们会认为系统已经被黑客入侵，从而**直接拒绝运行**！
>
> - **sudo 命令直接瘫痪**：/etc/sudoers 文件的权限要求非常严格。一旦你把它改成 777，系统会报错：sudo: /etc/sudoers is world writable，然后直接锁定 sudo。你将**彻底失去管理员权限**。
> - **SSH 远程登录直接断开**：SSH 服务的密钥文件一旦变成 777，SSH 服务会直接关闭。你将无法再通过网络登录这台服务器。
>
> **2. 没有任何“后悔药”**
>
> Linux 的文件和目录各有各的默认权限（有些是 644，有些是 600，有些是 440）。
> 一旦你用 -R 777 把它们一刀切全部覆盖了，**你没有任何办法一键恢复**。因为你根本不记得哪个文件原本是什么权限。唯一的解决办法就是**重装系统**。
>
> 即使不对系统目录操作，对我们自己的项目目录（比如 /data/project），直接运行 chmod -R 755 或 chmod -R 644 也是不合理的。
>
> 这是一个两难的尴尬局面：
>
> 还记得学的“目录与文件权限的区别”吗？
>
> - **文件夹（目录）**：必须拥有 **x（执行）权限**，我们才能 cd 进去。所以文件夹一般需要 **755**（rwxr-xr-x）。
> - **普通文件**：绝对不应该拥有 x（执行）权限（除非它是脚本或程序）。所以普通文件一般需要 **644**（rw-r--r--）。
>
> 如果你用一刀切的 -R：
>
> - 如果你执行 chmod -R 755 mydir：📂 文件夹变成了 755（可以 cd 进去，很好）。📄 但里面的 **普通文本、图片、网页文件也全变成了 755（带上了执行权限 x）**。这在安全上是极不规范的。
> - 如果你执行 chmod -R 644 mydir：📄 文件变成了 644（很好，不可执行）。📂 但 **所有的文件夹也变成了 644（没有了 x 权限）！你和你的程序再也 cd 不进任何一个子文件夹了！** 整个目录直接瘫痪。

更合理的做法：目录和文件分开设置。

```bash
find /data/project -type d -exec chmod 755 {} \;
find /data/project -type f -exec chmod 644 {} \;
```

> **1. find 命令是干什么的？**
>
> 简单来说，find 就是 **Linux 里的“搜索框”**（类似于你在 Windows 里按 Ctrl + F 搜文件）。
>
> 它的基本格式是：
>
> ```
> find【去哪里搜】【搜什么东西】find【去哪里搜】【搜什么东西】
> ```
>
> - **例子**：find /data -name "abc.txt"*翻译*：去 /data 目录里，帮我搜名字叫 abc.txt 的文件。
>
> ------
>
> **2. -type 不是查看类型的吗？**
>
> 您说得没错，Linux 里确实有用来“查看”文件类型的命令（比如 file）。
>
> 但在 find 命令的语境下，-type 是一个**“筛子”（过滤器）**。它不是用来查看类型，而是用来**限定搜寻的类型**。
>
> 因为在 Linux 里，“一切皆文件”，文件夹和普通文件混在一起。
>
> - **-type d**（**D**irectory）：告诉系统，“**我只要文件夹**，普通文件请全部过滤掉”。
> - **-type f**（**F**ile）：告诉系统，“**我只要普通文件**，文件夹请全部过滤掉”。
>
> 所以，find /data -type d 的意思就是：“去 /data 目录下，**把所有的文件夹都给我找出来**”。
>
> ------
>
> **3. -exec 又是什么？**
>
> 默认情况下，find 搜到东西后，只会把名字**打印在屏幕上**让你看看，什么都不会做。
>
> 但如果我们搜到东西后，**想顺便对它们做点什么**（比如：把搜到的文件全部删除，或者把搜到的文件全部修改权限），该怎么办？
>
> 这就是 **-exec**（**exec**ute，执行）的作用。它是一个**桥梁**，意思是：
>
> > “请对我搜出来的每一个东西，**执行**后面指定的命令。”
>
> ------
>
> **4. 最让人崩溃的两个符号：{} 和 \;**
>
> 在 -exec 的后面，为什么会多出 {} 和 \; 这样奇形怪状的符号？
>
> **① {} —— 占位符（空箱子）**
>
> find 在搜寻时，是“搜出一个，处理一个”的。
>
> - 当它搜到 a.txt 时，它把 a.txt 放进 {} 这个盒子里，然后执行 chmod 644 a.txt；
> - 接着它搜到 b.txt，它把 b.txt 放进 {} 里，执行 chmod 644 b.txt……
> - 所以，**{} 就代表“当前正在被处理的那个文件/文件夹”**。
>
> **② \; —— 结束标记（句号）**
>
> 因为 -exec 后面可以接很长的命令，系统需要知道你的命令到哪里算结束。
>
> - 在 Linux 里，**分号 ;** 代表命令结束。
> - 但因为分号 ; 在 Shell 里有特殊用途（用来隔开多条命令），所以为了不让 Shell 误会，我们必须在分号前面加一个**反斜杠 \** 进行转义。
> - 连起来写的 **\;**，就相当于给这个命令画上的一个**“句号”**。
>
> ------
>
> **5. 终极“人话翻译”**
>
> 现在，我们把这行神级命令重新拼起来，做一次逐字翻译：
>
> ```
> find  /data/project  -type d  -exec  chmod 755  {}   \;
> ```
>
> - **find /data/project**：去 /data/project 目录下搜寻。
> - **-type d**：只搜寻**文件夹**。
> - **-exec**：搜出来之后，请执行后面的动作……
> - **chmod 755**：修改权限为 755。
> - **{}**：修改的对象就是刚才搜出来的那个文件夹。
> - **\;**：命令到这里结束。
>
> 在 Linux 实际运维中，高手们更喜欢用另一个“神器”来代替它们。这个神器叫 **xargs**。
>
> ```
> find /data/project -type d | xargs chmod 755
> ```
>
> 这个命令是怎么工作的？（非常符合直觉）
>
> 1. **find /data/project -type d**：搜出所有的文件夹。
> 2. **|（管道符）**：把搜出来的文件夹列表，像流水线一样输送给下一步。
> 3. **xargs chmod 755**：**xargs 是个自动拼接怪**。它会把前面传过来的文件夹，自动排成一排，一并贴在 chmod 755 的后面。系统在后台实际执行的是：chmod 755 文件夹1 文件夹2 文件夹3...

## 6.5 chown：修改所有者和所属组

```bash
chown 新所有者 文件
chown 新所有者:新所属组 文件
chown -R 新所有者:新所属组 目录
```

示例：

```bash
sudo chown alice file.txt
sudo chown alice:dev file.txt
sudo chown -R alice:dev /data/project
```

普通用户通常不能随便把文件所有者改成别人，`chown` 常需要 root 权限。

## 6.6 chgrp：修改所属组

```bash
chgrp 新所属组 文件
chgrp -R 新所属组 目录
```

示例：

```bash
sudo chgrp dev file.txt
sudo chgrp -R dev /data/project
```

如果同时要改所有者和所属组，一般用 `chown user:group` 更方便。

> **在互联网公司里最真实的“工作交接”故事**。
>
> ------
>
> **🎭 故事背景**
>
> - 公司里的老员工 **tom** 离职了。
> - 新员工 **alice** 接替了他的工作。
> - 他们俩都在研发部 **dev** 组。
> - 现在，系统管理员（你）需要把 tom 留下的资产，全部过户给 alice。
>
> ------
>
> **场景一：把单个文件的“所有者（主人）”改成 Alice**
>
> tom 留下了一个工作总结文件 report.txt。
> 我们用 ls -l 查看一下这个文件当前的“所有者”和“所属组”：
>
> ```
> -rw-r--r--  tom  tom  report.txt
> # 主人是 tom，所属组也是 tom
> ```
>
> 现在，Alice 需要对这个文件有绝对权力（所有者）。
>
> - **你输入的命令**：`sudo chown alice report.txt`*(注：普通用户不能随便把自己的东西送给别人，所以必须用 sudo 找系统管理员来“过户”)*
> - **执行后的状态**：`-rw-r--r--  alice  tom  report.txt # 主人成功变成了 alice！但组还是 tom`
>
> ------
>
> **场景二：把单个文件的“所属组（家庭）”改成 dev 研发组**
>
> 现在，虽然主人是 Alice 了，但这个文件的组依然是 tom。我们希望把组改成全研发部 **dev** 都可以访问。
>
> - **你输入的命令**（使用 chgrp 修改组）：codeBash`sudo chgrp dev report.txt`
> - **执行后的状态**：codeText`-rw-r--r--  alice  dev  report.txt # 主人是 alice，所属组变成了 dev！`
>
> ------
>
> **场景三：一步到位！同时修改“主人”和“所属组”（最常用！）**
>
> 在实际工作中，大家嫌分两步太麻烦了，通常会使用 **chown 的“合体”写法**（用冒号 : 隔开所有者和所属组）：
>
> 假设有一个新文件 config.ini：
>
> ```
> -rw-r--r--  tom  tom  config.ini
> ```
>
> 我们想一步到位，把主人改成 alice，组改成 dev。
>
> - **你输入的命令**：codeBash`sudo chown alice:dev config.ini`
> - **执行后的状态**：codeText`-rw-r--r--  alice  dev  config.ini # 一秒钟过户完毕！`
>
> ------
>
> **场景四：整顿整个项目文件夹（递归修改 -R）**
>
> tom 在服务器上留下了一个庞大的项目文件夹，路径是 /data/project，里面有成百上千个源代码文件和子目录。
> 如果一个一个去改，手会断掉。这时候，我们祭出 **-R（递归）** 大招：
>
> - **你输入的命令**：codeBash`sudo chown -R alice:dev /data/project`
> - **执行后的结果**：/data/project 这个文件夹的主人变成了 alice，组变成了 dev。里面所有的子文件（比如 main.py、index.html）、所有的子文件夹（比如 static/、images/）以及里面的所有孙子文件……**全部在瞬间一次性全部过户给了 alice 和 dev 组！**
>
> ------
>
> **💡 为什么这里必须用 sudo？**
>
> Linux 系统非常注重隐私和安全。
>
> - 如果不限制 chown，小明就可以写一个木马程序，然后用 chown root virus 塞给系统管理员，系统就会彻底崩溃。
> - 所以，**“过户/改所有者”是一项极其敏感的权力，只有超级管理员 sudo（root）才能执行。**

## 6.7 本部分面试题

### 题 1：`chmod 755` 和 `chmod 777` 有什么区别？为什么生产环境不建议 777？

**答案：** `755` 表示所有者可读写执行，组用户和其他用户可读可执行但不可写；`777` 表示所有人都可读写执行。生产环境不建议 `777`，因为任何用户都能修改、删除或替换文件，容易造成误操作、权限绕过或安全漏洞。更好的做法是按用户和用户组最小授权。

### 题 2：把 `file.sh` 设置为所有者可读写执行，组和其他用户只读执行，命令是什么？

```bash
chmod 755 file.sh
```

或者：

```bash
chmod u=rwx,g=rx,o=rx file.sh
```

### 题 3：如何只把目录设为 755、普通文件设为 644？

```bash
find . -type d -exec chmod 755 {} \;
find . -type f -exec chmod 644 {} \;
```

# 07 文件掩码 umask

## 7.1 umask 是什么

`umask` 是文件创建权限掩码，用来决定新建文件或目录时默认要屏蔽哪些权限。

查看当前 umask：

```bash
umask
```

常见输出：

```bash
0022
```

`0022` 的含义：屏蔽 group 的写权限，屏蔽 others 的写权限。

## 7.2 默认最大权限

| 类型 | 默认最大权限 | 原因 |
|---|---|---|
| 普通文件 | `666`，即 `rw-rw-rw-` | 新文件默认不给执行权限，避免文本文件变成可执行程序 |
| 目录 | `777`，即 `rwxrwxrwx` | 目录需要 `x` 才能进入 |

## 7.3 umask 计算公式

严格说不是普通减法，而是位运算：

```text
最终权限 = 默认最大权限 & ~umask
```

新手可以先用“去掉 umask 指定的权限”理解。

### 7.3.1 umask 022

```text
文件：666 & ~022 = 644
目录：777 & ~022 = 755
```

所以：

```bash
umask 022
touch a.txt      # 默认 644
mkdir dir        # 默认 755
```

### 7.3.2 umask 002

```text
文件：666 & ~002 = 664
目录：777 & ~002 = 775
```

适合组内协作。

### 7.3.3 umask 027

```text
文件：666 & ~027 = 640
目录：777 & ~027 = 750
```

含义：所有者权限完整，组用户可读/进入，其他用户无权限。

## 7.4 临时修改和永久修改

临时修改当前 Shell：

```bash
umask 022
```

只对当前 Shell 和它后续创建的子进程有效。永久修改个人用户默认 umask，可以写入 `~/.bashrc`、`~/.profile`；系统级配置常见于 `/etc/profile`、`/etc/bashrc`、`/etc/login.defs`，不同发行版可能不同。

## 7.5 umask 常见误区

| 误区 | 正确理解 |
|---|---|
| `666 - 022 = 644` 永远成立 | 只是常见情况下像减法，本质是位掩码 |
| 新文件默认可以有执行权限 | 普通文件默认最大权限是 `666`，不会自动有 `x` |
| umask 会修改已有文件权限 | umask 只影响之后新建的文件/目录 |
| umask 越小越安全 | umask 越小，默认开放的权限越多；通常越大越保守 |

## 7.6 本部分面试题

### 题 1：umask 为 027，新建文件和目录默认权限分别是多少？

**答案：** 普通文件默认最大权限是 `666`，目录默认最大权限是 `777`。`umask 027` 表示屏蔽所属组写权限和其他用户全部权限。因此新建文件默认是 `640`，新建目录默认是 `750`。

### 题 2：为什么新建普通文件默认不是 777？

**答案：** 为了安全，普通文件默认最大权限是 `666`，不会自动带执行权限。否则任何新建文本文件都可能变成可执行程序，存在安全风险。需要执行权限时应显式 `chmod +x`。

# 08 特殊权限：粘滞位、SUID、SGID

> 原文重点讲了粘滞位。面试中经常会顺带问 SUID、SGID，所以这里一起补充。

## 8.1 粘滞位 sticky bit 是什么

粘滞位用于目录时，可以限制普通用户删除或重命名别人的文件。典型场景是 `/tmp` 目录。

查看 `/tmp`：

```bash
ls -ld /tmp
```

典型结果：

```text
drwxrwxrwt  root root  /tmp
```

最后的 `t` 表示设置了粘滞位。

## 8.2 为什么 `/tmp` 需要粘滞位

`/tmp` 是临时目录，很多用户和程序都需要往里面写文件，因此它通常允许所有人写入。如果没有粘滞位，任何用户都可能删除别人在 `/tmp` 下创建的文件，这很危险。设置粘滞位后，普通用户仍然可以创建自己的文件，但不能删除别人的文件。能删除的人通常是：文件所有者、目录所有者、root。

## 8.3 设置和取消粘滞位

设置：

```bash
chmod +t shared_dir
```

数字写法：

```bash
chmod 1777 shared_dir
```

取消：

```bash
chmod -t shared_dir
```

## 8.4 `t` 和 `T` 的区别

| 显示 | 含义 |
|---|---|
| `t` | others 有执行权限，并且设置了粘滞位 |
| `T` | others 没有执行权限，但设置了粘滞位 |

例如：

```text
drwxrwxrwt  # t：有 x + sticky
drwxrwxrwT  # T：无 x + sticky
```

目录没有 `x` 权限时，用户无法正常进入目录，所以 `T` 往往表示权限配置不太合理。

## 8.5 SUID 是什么

SUID 用于可执行文件，含义是：用户执行该程序时，进程临时拥有文件所有者的权限。

典型例子：

```bash
ls -l /usr/bin/passwd
```

可能看到：

```text
-rwsr-xr-x root root /usr/bin/passwd
```

`rws` 中的 `s` 表示 SUID。普通用户可以执行 `passwd` 修改自己的密码，而真正写入 `/etc/shadow` 需要 root 权限，所以 `passwd` 通过 SUID 临时获得 root 权限完成必要操作。

设置 SUID：

```bash
chmod u+s program
chmod 4755 program
```

取消：

```bash
chmod u-s program
```

安全提醒：不要随便给脚本或自写程序设置 SUID，容易造成严重提权漏洞。

## 8.6 SGID 是什么

SGID 用于文件：执行时临时拥有文件所属组权限。SGID 用于目录：在该目录中新建的文件/目录默认继承父目录的所属组，常用于团队协作目录。

设置目录 SGID：

```bash
chmod g+s project_dir
chmod 2775 project_dir
```

查看可能显示：

```text
drwxrwsr-x devteam project_dir
```

## 8.7 特殊权限数字位

| 特殊权限 | 数字 | 示例 |
|---|---:|---|
| SUID | 4 | `4755` |
| SGID | 2 | `2775` |
| Sticky bit | 1 | `1777` |

组合也可以相加，例如 `6755` 表示 SUID + SGID。

## 8.8 本部分面试题

### 题 1：`/tmp` 为什么是 `1777` 而不是 `777`？

**答案：** `777` 表示所有用户都可以在目录中读、写、进入，因此任何用户都可能删除别人创建的文件。`1777` 在 `777` 基础上增加粘滞位，允许所有用户创建临时文件，但只有文件所有者、目录所有者或 root 能删除/重命名对应文件。这样既保证公共临时目录可用，又避免用户互相删除文件。

### 题 2：SUID 有什么作用？为什么危险？

**答案：** SUID 让用户执行某个可执行文件时，进程临时获得该文件所有者的权限，例如 `/usr/bin/passwd` 需要修改受保护的密码文件，所以设置了 SUID。危险在于如果一个有漏洞的程序被设置为 root SUID，普通用户可能利用漏洞获得 root 权限，因此生产环境要严格控制 SUID 文件数量和来源。

# 09 sudo：普通用户的权限提升机制

## 9.1 sudo 是什么

`sudo` 允许普通用户在授权范围内，以其他用户身份执行命令，默认通常是 root。

```bash
sudo useradd testuser
sudo systemctl restart nginx
```

用户能不能 sudo，不是看他想不想，而是看 sudoers 配置是否授权。

## 9.2 sudoers 文件

sudo 权限主要由下面文件控制：

```bash
/etc/sudoers
/etc/sudoers.d/
```

修改 sudoers 必须用：

```bash
sudo visudo
```

不要直接 `vim /etc/sudoers`，因为写错语法可能导致 sudo 整体不可用；`visudo` 会做语法检查。

## 9.3 sudoers 基本格式

典型规则：

```text
username  ALL=(ALL)  ALL
```

含义：

| 字段 | 含义 |
|---|---|
| `username` | 被授权的用户 |
| 第一个 `ALL` | 可以在哪些主机上执行 |
| `(ALL)` | 可以以哪些目标用户身份执行 |
| 最后 `ALL` | 可以执行哪些命令 |

示例：允许 `alice` 执行所有命令：

```text
alice ALL=(ALL) ALL
```

允许 `alice` 只执行 useradd：

```text
alice ALL=(ALL) /usr/sbin/useradd
```

允许 wheel 组用户 sudo：

```text
%wheel ALL=(ALL) ALL
```

`%wheel` 表示用户组，不是普通用户名。

## 9.4 sudo 和 su 区别

| 对比 | `su` | `sudo` |
|---|---|---|
| 含义 | 切换用户 | 以授权身份执行命令 |
| 常用方式 | `su - root` | `sudo command` |
| 密码 | 目标用户密码 | 当前用户密码 |
| 安全性 | 容易长时间停留在 root | 更适合最小权限和审计 |
| 日志 | 不如 sudo 精细 | sudo 通常有日志记录 |

## 9.5 sudo 使用注意点

| 注意点 | 说明 |
|---|---|
| 优先精确授权 | 不要随便给 `ALL=(ALL) ALL` |
| 使用命令绝对路径 | sudoers 中写 `/usr/sbin/useradd` 比 `useradd` 更明确 |
| 用用户组管理权限 | 多人协作时用 `%group` 更好维护 |
| 不要随便 NOPASSWD | 免密 sudo 方便但风险更高 |
| 用 `visudo` 修改 | 防止语法错误导致 sudo 崩掉 |

## 9.6 本部分面试题

### 题 1：sudo 为什么比直接使用 root 更安全？

**答案：** sudo 可以按用户、用户组、命令范围做细粒度授权，并且通常会记录执行日志。用户只在执行特定命令时临时获得高权限，不需要长期停留在 root Shell 中。这样既满足管理需求，又降低误操作和权限滥用风险。

### 题 2：为什么 sudoers 里建议写命令绝对路径？

**答案：** 使用绝对路径可以避免 PATH 劫持或命令歧义。例如 `/usr/sbin/useradd` 比 `useradd` 更明确，sudoers 授权时也更容易审计。

# 10 综合案例：Shell 命令与权限管理实战

## 10.1 案例一：创建项目协作目录

需求：创建 `/data/project`，让 `devteam` 组成员可以协作读写，其他人不能访问；新建文件自动继承 `devteam` 组。

```bash
sudo groupadd devteam
sudo mkdir -p /data/project
sudo chown root:devteam /data/project
sudo chmod 2770 /data/project
```

解释：

| 命令 | 作用 |
|---|---|
| `groupadd devteam` | 创建项目组 |
| `mkdir -p /data/project` | 创建项目目录 |
| `chown root:devteam` | 设置所属组为 devteam |
| `chmod 2770` | `2` 表示 SGID；`770` 表示所有者和组有完整权限，其他人无权限 |

把用户加入组：

```bash
sudo usermod -aG devteam alice
sudo usermod -aG devteam bob
```

注意：用户重新登录后组权限通常才会刷新。

## 10.2 案例二：批量修正目录和文件权限

需求：`/data/web` 下目录权限设为 `755`，普通文件权限设为 `644`，脚本文件 `.sh` 权限设为 `755`。

```bash
#!/bin/bash
set -euo pipefail

TARGET_DIR="/data/web"

if [ ! -d "$TARGET_DIR" ]; then
    echo "错误：目录不存在：$TARGET_DIR" >&2
    exit 1
fi

find "$TARGET_DIR" -type d -exec chmod 755 {} \;
find "$TARGET_DIR" -type f -exec chmod 644 {} \;
find "$TARGET_DIR" -type f -name "*.sh" -exec chmod 755 {} \;

echo "权限修正完成：$TARGET_DIR"
```

解释：

| 代码 | 含义 |
|---|---|
| `set -euo pipefail` | 提高脚本健壮性：错误退出、未定义变量报错、管道错误可感知 |
| `[ ! -d "$TARGET_DIR" ]` | 判断目标目录不存在 |
| `>&2` | 错误信息输出到 stderr |
| `find ... -type d` | 找目录 |
| `find ... -type f` | 找普通文件 |
| `-exec chmod ... {} \;` | 对找到的每个结果执行 chmod |

## 10.3 案例三：日志命令输出同时显示和保存

需求：执行脚本时，既在屏幕显示输出，也保存到日志。

```bash
bash deploy.sh 2>&1 | tee deploy.log
```

追加保存：

```bash
bash deploy.sh 2>&1 | tee -a deploy.log
```

解释：

| 部分 | 含义 |
|---|---|
| `2>&1` | stderr 合并到 stdout |
| `| tee deploy.log` | 一边显示到屏幕，一边写入文件 |
| `-a` | 追加写入，不覆盖旧日志 |

## 10.4 案例四：批量创建用户并设置私有目录

需求：创建 `user1` 到 `user5`，每个人有 `/home/userX/work` 私有目录，别人不能进入。

```bash
#!/bin/bash
set -euo pipefail

for i in {1..5}; do
    username="user${i}"

    if ! id "$username" &>/dev/null; then
        sudo useradd -m "$username"
    fi

    sudo mkdir -p "/home/${username}/work"
    sudo chown "${username}:${username}" "/home/${username}/work"
    sudo chmod 700 "/home/${username}/work"

    echo "已完成：${username}"
done
```

说明：

| 权限 | 含义 |
|---|---|
| `700` | 只有所有者能读、写、进入 |
| `chown user:user` | 目录归该用户和同名组所有 |
| `id username` | 判断用户是否存在 |

# 11 高频面试题与笔试题完整解析

## 11.1 Shell 运行原理类

### 题 1：执行 `ls -l` 时 Shell 做了什么？

**答案：** Shell 先读取用户输入，然后解析命令名 `ls` 和参数 `-l`；判断 `ls` 不是内置命令后，根据 `PATH` 查找可执行文件，通常找到 `/usr/bin/ls`；Shell 通过 `fork()` 创建子进程，在子进程中通过 `exec()` 执行 `ls`；父进程等待子进程结束，最后得到退出状态码并继续显示提示符。

### 题 2：如何判断一个命令是内置命令还是外部命令？

```bash
type cd
type ls
type -a ls
command -v ls
```

`type` 更适合解释 Shell 视角下的命令类型，能显示 alias、function、builtin、外部路径。

### 题 3：`$?` 是什么？

**答案：** `$?` 表示上一条命令的退出状态码。`0` 通常表示成功，非 `0` 表示失败。脚本中经常根据 `$?` 或直接用 `if command; then ... fi` 判断命令是否成功。

### 题 4：为什么执行不存在的命令通常返回 127？

**答案：** Shell 没有找到对应命令时，一般返回 `127`。如果命令存在但没有执行权限，常见返回码是 `126`。

## 11.2 权限基础类

### 题 5：解释 `drwxr-xr-x`。

**答案：** 第一位 `d` 表示目录；所有者权限 `rwx`，可以列出、创建删除、进入目录；所属组权限 `r-x`，可以列出和进入，但不能创建删除；其他用户权限 `r-x`，同样可以列出和进入，不能写。数字权限是 `755`。

### 题 6：`chmod 640 file.txt` 表示什么？

**答案：** 所有者 `rw-` 可读写，所属组 `r--` 只读，其他用户 `---` 无权限。

### 题 7：目录的 `x` 权限有什么用？

**答案：** 目录的 `x` 表示可以进入目录或访问目录中的具体路径，也叫 search 权限。没有 `x`，即使有 `r`，也无法正常访问目录下文件的元信息或进入目录。

### 题 8：删除文件需要文件本身的写权限吗？

**答案：** 通常不需要。删除文件主要需要父目录的 `w+x` 权限，因为删除操作修改的是父目录中的目录项。例外是设置了粘滞位的目录，例如 `/tmp`，普通用户不能删除别人的文件。

## 11.3 umask 与特殊权限类

### 题 9：umask 022 下新建文件和目录权限是多少？

**答案：** 新建普通文件默认最大权限 `666`，屏蔽 `022` 后是 `644`；新建目录默认最大权限 `777`，屏蔽 `022` 后是 `755`。

### 题 10：什么是粘滞位？

**答案：** 粘滞位用于目录时，限制普通用户删除或重命名别人的文件。典型目录是 `/tmp`，权限通常是 `1777`，显示为 `drwxrwxrwt`。

### 题 11：SUID、SGID、Sticky bit 的数字分别是多少？

**答案：** SUID 是 `4`，SGID 是 `2`，Sticky bit 是 `1`。例如 `4755` 设置 SUID，`2775` 设置 SGID，`1777` 设置粘滞位。

## 11.4 sudo 与脚本类

### 题 12：为什么要用 `visudo` 修改 sudoers？

**答案：** `visudo` 会在保存时检查 sudoers 语法，避免因为配置错误导致 sudo 无法使用。直接编辑 `/etc/sudoers` 风险较高。

### 题 13：`source script.sh` 和 `bash script.sh` 区别是什么？

**答案：** `bash script.sh` 会启动新的 bash 子进程执行脚本，脚本中的变量和 `cd` 不会影响当前 Shell；`source script.sh` 在当前 Shell 中执行，会影响当前环境，因此常用于加载环境变量配置。

### 题 14：脚本中 `set -euo pipefail` 有什么作用？

**答案：** `set -e` 表示命令失败时退出；`set -u` 表示使用未定义变量时报错；`pipefail` 表示管道中任意命令失败都会让整个管道失败。它们能减少脚本静默失败的问题。

### 题 15：写一个脚本，批量把 `.log` 文件权限设置为 `640`。

```bash
#!/bin/bash
set -euo pipefail

TARGET_DIR="${1:-.}"
find "$TARGET_DIR" -type f -name "*.log" -exec chmod 640 {} \;
echo "done"
```

执行：

```bash
bash fix_log_perm.sh /var/log/myapp
```

# 12 易错点总表

| 易错点 | 正确理解 |
|---|---|
| Shell 就是终端 | 终端是窗口/设备，Shell 是里面运行的命令解释器 |
| `which` 能识别所有命令类型 | `which` 主要查路径，`type` 更能反映 Shell 实际解析 |
| `cd` 可以是外部命令 | `cd` 必须影响当前 Shell，所以通常是内置命令 |
| 管道会传 stderr | 默认管道只传 stdout，stderr 需要 `2>&1` 或 `|&` |
| `cmd >log 2>&1` 和 `cmd 2>&1 >log` 一样 | 不一样，重定向从左到右处理 |
| 文件有写权限才能删除 | 删除看父目录 `w+x` 权限，和文件自身写权限不是一回事 |
| 目录 `x` 是执行目录 | 目录 `x` 是进入/搜索权限 |
| umask 是简单减法 | 本质是位掩码：默认权限 `& ~umask` |
| 新文件默认 777 | 普通文件默认最大是 666，目录默认最大是 777 |
| 777 最省事 | 777 风险极高，生产环境应最小授权 |
| sudo 就是 root | sudo 是授权机制，不等于用户本身永远是 root |
| 直接 vim sudoers 没问题 | 应使用 `visudo` 防止语法错误 |
| `/tmp` 是 777 | `/tmp` 通常是 1777，多了粘滞位 |
| SUID 可以随便加 | SUID 风险极高，可能造成提权漏洞 |

# 13 最后一页速记版

```text
Shell：命令解释器，不是内核。
命令执行：读取 → 解析 → 查找 → 执行 → 返回状态码。
内置命令：cd、pwd、alias、history，在当前 Shell 执行。
外部命令：ls、grep，通常 fork + exec + wait。
PATH：Shell 查找外部命令的目录列表。
$?：上一条命令退出码，0 成功，非 0 失败。
stdin/stdout/stderr：0/1/2。
管道 |：stdout → stdin。
重定向 > 覆盖，>> 追加，2> 错误，2>&1 合并错误到标准输出。
重定向顺序从左到右：cmd >log 2>&1 和 cmd 2>&1 >log 不一样。
权限三组：user/group/others。
rwx 数字：r=4，w=2，x=1。
644：rw-r--r--；755：rwxr-xr-x；700：rwx------。
目录 x：进入/搜索；目录 w+x：创建、删除、重命名目录项。
删除文件看父目录权限，不主要看文件自身写权限。
chmod 改权限，chown 改所有者，chgrp 改所属组。
umask：影响新建文件/目录默认权限；文件最大 666，目录最大 777。
sticky bit：1777，/tmp 常用，禁止普通用户删除别人文件。
SUID：4xxx，执行时临时拥有文件所有者权限。
SGID：2xxx，目录中新文件继承所属组。
sudo：按 sudoers 授权临时提权；修改 sudoers 用 visudo。
```
